Welcome to Topic 4.3, Delegation, Service Accounts and Joining. Your domain sa1.lab exists, but only DC01 belongs to it. You will see why a computer must use the domain controller for DNS before it can join, and you will join SRV01 and CLIENT01 in the GUI and with PowerShell. You will put computer objects in the right OU. Then you will hand one small task to the help desk, and read the permission it creates. Last, you will choose a service account and build a group managed service account for SRV01.

Joining starts with a question: where is a domain controller for sa1.lab? The computer asks its DNS server for a special SRV record, underscore ldap, underscore tcp, dc, underscore msdcs. DC01 holds that record in its Active Directory zones and answers: dc01.sa1.lab, port 389. If DNS is blank, or still points at SRV01 from Learning Plan 3, nobody knows sa1.lab, and you get the error that a domain controller could not be contacted. So the rule for every domain member is simple: DNS server 192.168.50.10. Never a public DNS server.

The classic way to join is System Properties. Type sysdm.cpl, or on Windows 11 go to Settings, System, About, and select Domain or workgroup. On the Computer Name tab, select Change. In the Computer Name and Domain Changes dialog, under Member of, select Domain and type sa1.lab. Select OK. Windows asks for an account that may join computers; in the lab that is SA1 backslash Administrator. You get a welcome message, and then a restart. Until that restart, the join is not finished.

Here is the same job in PowerShell on SRV01. First, Set-DnsClientServerAddress points the Ethernet adapter at 192.168.50.10. Test before you join: Resolve-DnsName with type SRV for the DC record. If DC01 and port 389 come back, the join will find the DC. Now Add-Computer, dash DomainName sa1.lab. Dash OUPath puts the computer object straight into OU Servers. Dash Credential asks for the password in a box, and dash Restart restarts SRV01 for you. After the restart, sign in as SA1 backslash Administrator and check the domain.

Every joined computer gets a computer object in Active Directory, with an account name like SRV01 dollar sign. Without a choice, it lands in Computers. That is a container, not an OU, and you cannot link a Group Policy to it. One fix is to pre-stage. Before the join, right-click OU Workstations, choose New, Computer, and type CLIENT01. The dialog also says who may join this computer; the default is Domain Admins. When CLIENT01 joins later, it reuses this object, already in the right OU.

In PowerShell, New-ADComputer with dash Path pre-stages CLIENT01 in Workstations. Get-ADComputer with a filter of star lists every computer object and its distinguished name, so you can see that DC01, SRV01 and CLIENT01 are where they belong, and nothing sits in CN equals Computers. If one does, pipe it to Move-ADObject with a target path, or in the console right-click it and choose Move. As a concept only, redircmp changes where every new join lands by default, for the whole domain.

Now delegation. The help desk needs to reset student passwords. The lazy answer is Domain Admins for Ben Ortiz. Then one stolen help desk password owns the whole domain. Least privilege means only the rights the job needs, only where they are needed. So bortiz is a member of GG-HelpDesk. That group gets one permission on OU Students, and the user objects inside, dpatel and emoss, inherit it. Always delegate to a group. When staff change, you change the group membership, not the permissions.

The Delegation of Control Wizard sets this up for you. In Active Directory Users and Computers, right-click OU Students and choose Delegate Control. On the Users or Groups page, select Add, type GG-HelpDesk and Check Names. On the Tasks to Delegate page, keep Delegate the following common tasks, and select just one: Reset user passwords and force password change at next logon. Nothing else. A custom task lets you pick object types and rights yourself, but the common task is exactly what we need. Then Finish.

What did the wizard actually do? It wrote permission entries on the OU. To see them, turn on View, Advanced Features. Then open the properties of Students, the Security tab, and Advanced. You find two entries for GG-HelpDesk. One allows Reset password. The other, shown as Special, lets the group read and write pwdLastSet, which is how force password change at next logon works. Both apply to Descendant User objects: the users inside the OU, not the OU itself or its groups.

The command-line tool dsacls lists every permission entry on an AD object. Point it at OU Students and filter with findstr for helpdesk. Two lines come back: special access for pwdLastSet, and Reset Password. In the full list, they sit in the section inherited to user. dsacls can also grant. The slide shows the same two rights in dsacls syntax: CA, control access, for Reset Password, and RP WP, read and write property, for pwdLastSet. In the lab you use the wizard and only read with dsacls.

A service account is the identity a service runs as. LocalSystem is the most powerful, too much for most apps. NetworkService and LocalService have low local rights; on the network one appears as the computer, the other as anonymous. A virtual account, NT SERVICE backslash name, gives one service its own identity on one server. A domain user works, but a person manages its password. Managed service accounts fix that: standalone for one server, group for one or more servers, and delegated, new in Server 2025.

Why not just make a domain user called svc-web? Because its password is typed by hand, never expires, and never changes. Attackers can request its Kerberos tickets and crack a weak password offline. A gMSA is different. Active Directory computes a long random password and changes it every 30 days by default. You need a KDS root key, created once per forest, then the gMSA object, which names who may retrieve the password: only SRV01 dollar. SRV01 installs it, and a service logs on as gmsa-web dollar with a blank password box.

On DC01, Get-KdsRootKey shows nothing in a new forest. Add-KdsRootKey creates the key. Normally DCs wait up to 10 hours before using it, so the key can replicate. In our one-DC lab we use a documented shortcut: dash EffectiveTime set to 10 hours ago. Do not do that in production; there you simply wait. Then New-ADServiceAccount gmsa-web, with dash DNSHostName and dash PrincipalsAllowedToRetrieveManagedPassword set to SRV01 dollar, in quotes. Get-ADServiceAccount confirms that SRV01 in OU Servers is the allowed principal.

Now switch to SRV01, signed in as SA1 backslash Administrator. SRV01 needs the Active Directory module, so install the feature RSAT-AD-PowerShell. If it asks for source files, add dash Source D colon backslash sources backslash sxs, the ISO in drive D. Then Install-ADServiceAccount gmsa-web, which prints nothing when it works. Test-ADServiceAccount gmsa-web should say True. True means SRV01 can get the password from a DC. Services log on as SA1 backslash gmsa-web dollar, with a dollar sign like a computer account.

Windows Server 2025 adds one more type, the delegated managed service account, or dMSA. Its job is migration. You create a dMSA for an old domain user service account, start the migration, then complete it. After that, the old password is blocked and the dMSA takes its place, without reinstalling the service. The difference from a gMSA: the secret stays on the domain controllers and is tied to the machines you allow. You cannot migrate a gMSA to a dMSA. In SA1 this is an overview only.

Here are four mistakes to avoid. One: joining while DNS points at the old server or at nothing. Set 192.168.50.10 first and test the SRV record. Two: leaving computers in CN equals Computers. Use OUPath, pre-stage, or move them. Three: putting help desk staff in Domain Admins, or delegating to one person. Delegate one task to a group on one OU. Four: Test-ADServiceAccount says False. Check the KDS root key, the allowed principal SRV01 dollar, and that SRV01 restarted after the join.

Time to check yourself on the whole topic. First, CLIENT01 uses 192.168.50.20 for DNS. Why does the join fail, and what is the fix? Second, bortiz can reset the password of dpatel but not of alee. Why? Third, why use a gMSA for a web service instead of a domain user account? And fourth, why did the lab date the KDS root key 10 hours in the past? Pause the video, answer all four in your own words, then continue.

Here are the answers. One: 192.168.50.20 has no sa1.lab zone, so CLIENT01 cannot find the SRV record of a DC. Set DNS to 192.168.50.10, then join. Two: the right is on OU Students only. dpatel is in Students and inherits it; alee is in Staff, where GG-HelpDesk has no rights. Three: nobody knows or types the gMSA password. AD changes it every 30 days, and only SRV01 dollar may retrieve it. Four: so the key works at once in a one-DC lab. In production, wait for replication.

Let's do it in the pod. On SRV01 I point DNS at DC01 and test the SRV record. DC01 answers on port 389, so I run Add-Computer with the OU path for Servers. I type the password in the box, and SRV01 restarts. On DC01, Get-ADComputer shows SRV01 in OU Servers. Next, I right-click Students, delegate the password reset task to GG-HelpDesk, and then find the two entries in Advanced Security Settings and with dsacls. Finally I create the KDS root key and gmsa-web, and on SRV01 Test-ADServiceAccount returns True.

To wrap up. Point DNS at 192.168.50.10 first, then join, with System Properties, Settings, or Add-Computer with an OU path. Computer objects belong in Servers or Workstations, not in the Computers container. Delegate one task to a group on one OU, and read the result with dsacls. For services, prefer virtual accounts and gMSAs over domain user accounts.
