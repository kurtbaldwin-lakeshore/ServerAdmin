Welcome to Topic 4.2, Users, Groups and OUs. In Topic 4.1 you built the domain sa1.lab. Now you fill it. You will learn the difference between the built-in containers and organizational units, and how to design OUs around what administrators need. You will read distinguished names and protect OUs from being deleted by accident. You will create users with the right logon names, in Active Directory Users and Computers, in the Administrative Center and in PowerShell. Then you will manage accounts day to day, and finish with group types, scopes and a nesting pattern called AGDLP.

Open a brand new domain and you already see several folders. Most of them are containers. Their names start with CN. Users holds new users and groups by default, including Domain Admins and Domain Users. Computers holds newly joined computers. Containers come with the domain, and you cannot link Group Policy to them or create your own. Organizational units, OUs, start with OU. You create them, you can link Group Policy to them, delegate control of them, and nest them. Domain Controllers is the one OU that exists from the start.

Build OUs for the jobs administrators do, not to copy the org chart. Our tree starts with an OU called Lakeshore. Staff holds Ann, Ben and Carla. Students holds the students, and in Topic 4.3 the help desk gets the right to reset passwords there. Groups keeps every group in one place. Servers and Workstations will get different policies later. Every object has a distinguished name, or DN. For Dev Patel it is CN equals Dev Patel, OU equals Students, OU equals Lakeshore, DC equals sa1, DC equals lab. The object comes first, then each parent up to the domain. Move the object and the DN changes.

To create an OU in Active Directory Users and Computers, right-click the domain, sa1.lab, and choose New, Organizational Unit. Create in shows where the OU will go. Type the name, Lakeshore. Notice the check box Protect container from accidental deletion. It is ticked by default, and you should leave it ticked. For a child OU like Staff, right-click Lakeshore instead. If you ever really need to delete a protected OU, turn on View, Advanced Features, open its properties, and clear the box on the Object tab first.

Here is the same job in PowerShell. New-ADOrganizationalUnit with dash Name Lakeshore and dash Path, the domain, creates the top OU. Store its distinguished name in a variable called root. Then one foreach loop creates the five child OUs under it. Get-ADOrganizationalUnit with dash SearchBase lists only what is under Lakeshore, with each distinguished name. Finally, try to remove the Servers OU. You get Access is denied. The cmdlet protects new OUs by default, just like the check box in ADUC. That is a safety net you want to keep.

Right-click Staff and choose New, User. Type the first and last name, and the Full name fills in. Full name is the object name, so Ann's DN starts with CN equals Ann Lee. User logon name plus the suffix is her user principal name, or UPN: alee at sa1.lab. It must be unique in the forest. The pre-Windows 2000 logon name is the sAMAccountName, SA1 backslash alee, with at most twenty characters. On the next page, type the password shown in your NetLab pod. In our labs, clear User must change password at next logon. For real new users, keep it ticked.

Active Directory Administrative Center, or ADAC, is the newer console for the same directory. You navigate with a breadcrumb at the top and act from the Tasks pane on the right. Its best feature for learners sits at the bottom: the Windows PowerShell History Viewer. Open it, and every action you take appears as the real cmdlet with the values you typed. Create Ben Ortiz, and you see New-ADUser with his name, path and logon name. Copy a line and reuse it. Commands that only read data are hidden until you tick Show All.

To create users in PowerShell, first read the password shown in your NetLab pod with Read-Host dash AsSecureString. You see only stars, and the password never appears in your script. Then put the user's details in a hash table and pass it to New-ADUser with the at sign. That is called splatting. Two keys matter most: AccountPassword and Enabled. Leave them out and the account is created, but disabled. Get-ADUser with dash Filter star and dash SearchBase lists everyone under Lakeshore, with UPN and Enabled status.

Most daily work starts with a right-click on a user. Disable Account blocks sign-in but keeps the account, its groups and its permissions. Use it when someone leaves or goes on leave, and Enable Account brings it back. Reset Password sets a new password, and the dialog can also unlock the account in the same step. Move sends the account to another OU, and drag and drop works too. And in Properties, the Account tab shows the logon names, the Unlock account check box and Account is disabled.

Each of those tasks has a cmdlet. Disable-ADAccount turns off dpatel. Get-ADUser with the filter Enabled equals false finds every disabled account. You will see Guest, krbtgt and DefaultAccount too, because they are disabled by default. Set-ADAccountPassword with dash Reset is an administrator reset, using the password you stored with Read-Host. Enable-ADAccount turns dpatel back on. Unlock-ADAccount clears a lockout but keeps the password. Move-ADObject takes the object's DN and a target path, and afterwards the DN changes. Every one of these works on any user you name.

Every group has a type and a scope. The type is security or distribution. Security groups can be used in permissions, and distribution groups are only email lists. The scope decides what a group can contain. A global group holds users, computers and other global groups from the same domain, so use it to collect people with the same role, like GG-Faculty. A domain local group can hold users, global groups and universal groups from anywhere in the forest, and you use it for permissions in its own domain, like DL-Shared-Read. Universal groups matter in forests with many domains. Domain Admins and Domain Users are global groups.

AGDLP is the order to nest groups. A for accounts: Carla, Dev and Erin. G for global groups: Carla goes into GG-Faculty, the students into GG-Students. DL for domain local: both global groups become members of DL-Shared-Read. P for permission: only DL-Shared-Read gets Read on the share. Why bother? People change all the time, so you add and remove them in one global group. Each resource keeps one simple permission entry. In a forest with many domains, universal groups go in the middle.

To create a group in ADUC, right-click the Groups OU and choose New, Group. Type the group name, for example GG-IT. The pre-Windows 2000 name fills in. Our prefixes, GG and DL, show the scope at a glance. Under Group scope, choose Global for the GG groups and Domain local for DL-Shared-Read. Under Group type, keep Security, the default. To add members, open the group's properties and use the Members tab, or right-click a user and choose Add to a group.

In PowerShell, New-ADGroup needs a name and a dash GroupScope: Global, DomainLocal or Universal. Add dash GroupCategory Security and a path to the Groups OU. One loop makes the four global groups, and one more command makes DL-Shared-Read. Add-ADGroupMember puts dpatel and emoss into GG-Students, then GG-Faculty and GG-Students into DL-Shared-Read. Get-ADGroupMember confirms the two group members. Now try the wrong direction: put DL-Shared-Read into GG-IT. You get a red error, because a global group cannot contain a domain local group.

Four common mistakes. One: leaving new accounts in the Users container. Create them in an OU, and move any strays, because Group Policy cannot be linked to Users. Two: a delete fails with protected from accidental deletion. That is the safety catch working. Clear it on the Object tab only when you really mean it. Three: running New-ADUser with no password and no dash Enabled. The account exists but is disabled. Four: giving permissions to users, or nesting the wrong way. Follow AGDLP.

Time to check yourself, using the Lakeshore tree you build in the lab. First, why does Lakeshore have a Students OU, instead of keeping students in the Users container? Second, Erin Moss is in the Students OU. What is her distinguished name? Third, can GG-Students be a member of DL-Shared-Read? And can it work the other way round? Fourth, you ran New-ADUser with only a name and a sAMAccountName. Where is the account, and can it sign in? Pause the video and answer all four.

Here are the answers. One: an OU can receive Group Policy and delegated control, so the help desk can reset student passwords there. The Users container cannot. Two: CN equals Erin Moss, OU equals Students, OU equals Lakeshore, DC equals sa1, DC equals lab. Three: yes, a domain local group can contain global groups. No, a global group can contain only users, computers and other global groups from the same domain. Four: the account is in the Users container, and it is disabled, because it has no password and you did not enable it.

To wrap up. Containers hold the defaults, and OUs take Group Policy and delegation, so design OUs around administration and keep them protected. Each user has a full name, a UPN like alee at sa1.lab, and a sAMAccountName like SA1 backslash alee. Every GUI task has a cmdlet, and the Administrative Center shows you which one. Nest groups with AGDLP. In Lab 4.2 you build this exact tree on DC01, in about sixty minutes. Later labs depend on it, so type the names carefully.
