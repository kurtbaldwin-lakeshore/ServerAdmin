Welcome to Topic 3.2, Zones and Records. In this topic you build the practice namespace lakeshore.test. You will compare primary, secondary and stub zones, and meet the record types you use every day. You will create forward and reverse zones with the New Zone Wizard, and add A, PTR, CNAME and MX records in DNS Manager and in PowerShell. Then you will copy the zone to SRV-CORE, and then follow one change from SRV01 to SRV-CORE through the serial number.

A zone is the part of the DNS namespace that one server answers for, with all its records. The primary zone is the writable copy: lakeshore.test on SRV01. A secondary zone is a read-only copy pulled by zone transfer, for a spare server and shared load. A stub zone only lists the servers for a zone. Our zones are file-backed text files. Active Directory-integrated zones need a domain controller, so they wait for Learning Plan 4.

Every record has a name, a type, a time to live and its data. The SOA record, start of authority, holds the primary server, the serial number and the timers. NS names a server that answers for the zone. Both come with the zone. A maps a name to IPv4; AAAA to IPv6. A CNAME is an alias for another name. MX names the mail server. PTR maps an address back to a name. SRV records arrive with Active Directory.

Each lab starts fresh. On SRV01, run Install-WindowsFeature, dash Name DNS, dash IncludeManagementTools. One command adds the DNS Server role, DNS Manager and the PowerShell module, and opens port 53 in the firewall. No restart is needed. Get-Service DNS shows the DNS Server service running, but it has no zones of its own yet. Now open Server Manager, Tools, DNS. Expand SRV01, and you see Forward Lookup Zones and Reverse Lookup Zones. That is where your zones will go.

Right-click Forward Lookup Zones and choose New Zone. After the welcome page, the wizard asks for the zone type. Primary zone creates the copy you can update on this server, which is what we want for lakeshore.test. Secondary zone copies a zone from another server; SRV-CORE uses that later. Stub zone holds only name server records. Store the zone in Active Directory is greyed out, because SRV01 is not a domain controller. So this zone lives in a file.

Next, type the zone name, lakeshore.test. The Zone File page suggests the zone name plus dot dns, so lakeshore.test.dns, in the Windows System32 dns folder. Keep that default. Then the Dynamic Update page. Secure updates need an Active Directory zone, and nonsecure updates would let any computer change records. So select Do not allow dynamic updates. Nothing registers itself; you create every record by hand. Finish the wizard, and the zone appears with its SOA and NS records already in place.

A reverse lookup turns an address back into a name. DNS names read from specific to general, but addresses read from general to specific, so the numbers are reversed under in-addr.arpa. The address 192.168.50.20 becomes 20.50.168.192.in-addr.arpa. The zone is 50.168.192.in-addr.arpa, and inside it the PTR record is simply named 20. In the wizard, right-click Reverse Lookup Zones, choose Primary zone and IPv4. Then type the Network ID in normal order, 192.168.50. The wizard fills in the reversed zone name for you.

Here are the same two zones in PowerShell. Add-DnsServerPrimaryZone with dash Name lakeshore.test, dash ZoneFile, and dash DynamicUpdate None creates the forward zone. For the reverse zone, use dash NetworkId 192.168.50.0 slash 24, and the cmdlet works out the reversed name. Get-DnsServerZone lists both; your list may also show a zone called TrustAnchors, which is normal. IsDsIntegrated says False, so they are file-backed, with one plain text file per zone.

To add a host, right-click lakeshore.test and choose New Host. Type only the name, srv01, and the full name fills in by itself. Type the IP address, 192.168.50.20. Now the important check box: Create associated pointer, PTR, record. It also adds record 20 to the reverse zone, so one dialog makes two records. That only works if the reverse zone exists, so create it first. Select Add Host. The dialog stays open for the next host, and Done closes it.

Two more record types. Right-click the zone and choose New Alias, CNAME. The alias is www, and the target host is srv01.lakeshore.test. The target is a name, never an IP address. Next, New Mail Exchanger, MX. Leave Host or child domain blank, so the record is for lakeshore.test itself. The mail server is mail.lakeshore.test, with priority 10; lower numbers are tried first. The mail server needs its own A record. In the pod it is 192.168.50.25, an unused address. DNS does not check.

In PowerShell, first store the two zone names in short variables. Add-DnsServerResourceRecordA with a name, an address and the dash CreatePtr switch makes the A and PTR records in one step, like the check box. Or use two steps: the A record, then Add-DnsServerResourceRecordPtr with the name 30 in the reverse zone. The CNAME cmdlet uses dash HostNameAlias for the target. The MX cmdlet uses the name dot, meaning the zone itself, plus the mail server and its preference number.

Before SRV-CORE can copy the zone, SRV01 must allow it. Open the properties of lakeshore.test and select the Zone Transfers tab. A zone transfer hands over every name and address in the zone, so be careful who gets it. Select Allow zone transfers, then Only to the following servers. Use Edit to add 192.168.50.21, which is SRV-CORE. Then select Notify, choose The following servers, and add the same address. In PowerShell, Set-DnsServerPrimaryZone does the same with dash SecureSecondaries TransferToSecureServers and the Notify parameters.

SRV-CORE has no DNS Manager, so this is all PowerShell. Use SConfig option fifteen. Install the DNS role with the same command as before. Then run Add-DnsServerSecondaryZone with the name lakeshore.test, a zone file name, and dash MasterServers 192.168.50.20. The master is the server it copies from. Get-DnsServerZone now shows ZoneType Secondary. After a short wait, Get-DnsServerResourceRecord lists the SOA, the A records, the CNAME and the rest. The data arrived by zone transfer. This copy is read-only.

How does a change reach SRV-CORE? Look at the Start of Authority tab. The serial number goes up by one with every change on SRV01, say from 10 to 11. Because of Notify, SRV01 tells 192.168.50.21 that the zone changed. SRV-CORE asks for the SOA, sees 11 is higher than its 10, and pulls the changes. If a notify gets lost, SRV-CORE checks anyway at the refresh interval, 15 minutes by default. Start-DnsServerZoneTransfer forces a check at once.

Now test. Resolve-DnsName with dash Server picks which DNS server to ask. Ask SRV-CORE, at 192.168.50.21, for srv01, and you get the A record. Ask for www, and you get two answers: the CNAME, then the A record it leads to. With dash Type MX you see the mail server and preference 10. For a PTR lookup of 192.168.50.20, ask SRV01. SRV-CORE has a copy of the forward zone only, so in our pod it simply cannot answer that one.

Four mistakes. One: checking the PTR box before the reverse zone exists. The A record is made, but the PTR fails. Create the reverse zone first. Two: typing the Network ID backwards. Type 192.168.50 in normal order, and the wizard reverses it. Three: building the secondary before SRV01 allows transfers. Fix the Zone Transfers tab, then run Start-DnsServerZoneTransfer on SRV-CORE. Four: adding records on SRV-CORE. The secondary is read-only. Make every change on SRV01, and let the serial number carry it across.

Time to check yourself. SRV01 holds lakeshore.test and the reverse zone, and SRV-CORE holds a secondary. First, why is Store the zone in Active Directory greyed out on SRV01? Second, NAS01 is 192.168.50.40. In which zone is its PTR record, and what is the record's name? Third, what does Resolve-DnsName www.lakeshore.test return, and why two records? And fourth, you add a record on SRV01. How does SRV-CORE find out, and what happens if the notify is lost? Pause the video now.

Here are the answers. One: SRV01 is not a domain controller. Active Directory-integrated zones need a writeable DC running DNS, so until Learning Plan 4 our zones are file-backed. Two: the PTR record is in 50.168.192.in-addr.arpa, named 40. Three: you get the CNAME, then the A record, because www is an alias for srv01. Four: the serial goes up and SRV01 sends a notify. If the notify is lost, SRV-CORE still checks at the refresh interval, every 15 minutes by default.

On SRV01, I install DNS and open DNS Manager. The wizard creates lakeshore.test as a file-backed primary with no dynamic updates, then the reverse zone, Network ID 192.168.50. I add srv01 with the PTR box checked, dc01 with dash CreatePtr, then mail without a PTR, the CNAME www and the MX record. I allow transfers only to 192.168.50.21. On SRV-CORE I add the secondary zone. One new record on SRV01, and SRV-CORE follows.

To wrap up. The primary zone is writable, a secondary is a read-only copy, and a stub only lists name servers. Our zones are file-backed. For a reverse zone, type the Network ID in normal order. The PTR check box, or dash CreatePtr, makes A and PTR records in one step. Allow zone transfers only to 192.168.50.21; the serial number and notify move each change. Lab 3.2 practices all of this in about fifty-five minutes.
