Welcome to Learning Plan 3 and Topic 3.1, How DNS Works. You find out why networks need name resolution at all. You learn to read a fully qualified domain name and to picture the DNS tree behind it. You follow a query from the cache on a Windows client up to the root of the internet. Then you get hands-on: you manage the client cache, install the DNS Server role on SRV01, tour DNS Manager, and test names with nslookup and Resolve-DnsName.

People remember names. Packets need IP addresses. So something has to translate srv01.lakeshore.test into 192.168.50.20. In Lab 2.3 you did that with the hosts file, a text file on one computer. But every computer has its own copy. Ten computers means ten files to edit, and one old line gives a wrong answer. DNS, the Domain Name System, keeps names on servers instead, and clients just ask. Change a record once, and every client sees it. When a service moves, its name can stay the same.

Let's take a name apart. In srv01.lakeshore.test, each part between the dots is a label. Read it from right to left. At the very end is a dot you usually do not type. That dot is the root of the tree. Next comes test, the top-level domain. Then lakeshore, the domain, and finally srv01, the host. The full name, down to the root, is a fully qualified domain name, or FQDN. And test is reserved for testing, so our practice names never clash with real ones.

When CLIENT01 needs an address, where does it look? First, in its own resolver cache. That cache holds recent answers, and Windows also loads the hosts file lines into it. If there is no answer, the client asks its DNS server, SRV01. SRV01 checks the zones it holds; a match is an authoritative answer. Then it checks its own cache. Still nothing? It asks forwarders, if any are set, or uses root hints. The first answer wins. In the pod, that last step fails: no internet.

Two kinds of query are at work. CLIENT01 sends a recursive query. It means: give me the final answer, or an error. The client asks once and waits. SRV01 does the legwork with iterative queries. A root server says, ask the servers for test. Those say, ask the server for lakeshore.test. That server gives the address. Each step is a referral, a pointer closer to the name. Then SRV01 answers the client. This is how the internet works; our pod has no root servers.

Every DNS record has a name, a TTL, a type, and data. Type A means an IPv4 address. An authoritative answer comes from the server that holds the zone. It is the source of truth. A cached answer is a copy from an earlier lookup, and nslookup calls it non-authoritative. It is fast, but it can be old. The TTL, or time to live, is how many seconds a cache may keep that copy. Windows also caches name does not exist answers, so clear the cache after you fix a record.

You can look inside the client cache. ipconfig slash displaydns lists every cached name. Here the entry for srv-core.lakeshore.test came from a hosts file line. Record type 1 means an A record. ipconfig slash flushdns clears the cache. But look closely. After the flush, Get-DnsClientCache still shows srv-core. Flushing removes answers learned from DNS servers, then Windows loads the hosts lines again. To remove a hosts answer, edit the file. Clear-DnsClientCache is the PowerShell way to flush. Use an administrator window for these.

A client only asks a DNS server that it knows about. On CLIENT01, open ncpa.cpl, then the Ethernet properties, then Internet Protocol Version 4. The IP address stays as it is. Under Use the following DNS server addresses, type 192.168.50.20 as the preferred DNS server. That is SRV01. The alternate server is only asked when the first one does not answer, and we leave it empty. Windows 11 Settings can change the same value. In PowerShell, Set-DnsClientServerAddress does it, and Get-DnsClientServerAddress reads it back.

Now the server side. On SRV01, open Server Manager, then Manage, then Add Roles and Features. You know this wizard from Topic 2.1. On Server Selection, pick SRV01. On Server Roles, select DNS Server, then Add Features to get the management tools. The wizard adds a DNS Server page; read it and select Next. Then Install. No restart is needed. A DNS server needs a static IP address, because clients point at it by address. SRV01 has had one since Lab 1.4.

Here is the same job in one line. Install-WindowsFeature, dash Name DNS, dash IncludeManagementTools. The result says Success, and Restart Needed says No. The feature result lists DNS Server and DNS Server Tools. To check, run Get-WindowsFeature for DNS and RSAT-DNS-Server. An X in the brackets means installed. Finally, Get-Service shows the service named DNS, with the display name DNS Server, is running. It is running, but it has no zones yet. Keep that in mind, because it decides what this server can answer.

Open DNS Manager from Server Manager, Tools, DNS. The left pane shows SRV01. Under it, Forward Lookup Zones turn names into addresses, and Reverse Lookup Zones turn addresses back into names. Both are empty today. Conditional Forwarders is where you send one domain to a specific server, in Lab 3.3. Global Logs holds DNS Events, the DNS Server log, the first place to look when the service has a problem. To see the server settings, right-click SRV01 and choose Properties.

The Properties dialog has seven tabs; domain controllers add an eighth, Security. Four matter today. Interfaces shows that the server listens on all IP addresses. Keep that. Forwarders is empty, and Use root hints if no forwarders are available is checked. On Advanced, Disable recursion is off, so SRV01 looks up names for its clients. Root Hints lists the thirteen root servers, a dot root-servers dot net through m. They are built into Windows, and they are real internet servers, so our pod cannot reach them.

Put it together. SRV01 runs DNS but holds no zones, so it is a caching-only server. It can only recurse and cache. In the pod, recursion leads to root servers it cannot reach. So every name fails. It may fail after several seconds of retries, or quickly. That is a timeout, or a server failure. NXDOMAIN is different: DNS name does not exist. That is a real, fast answer from the server that holds the zone. A timeout points at the network or server.

Two tools test DNS itself. nslookup asks the DNS server directly, skipping the hosts file and the cache. In Lab 3.1 it shows Server UnKnown, because SRV01 has no reverse record yet; Lab 3.2 fixes that. Then the request times out. Type nslookup alone for an interactive prompt, and exit to leave it. Resolve-DnsName is the PowerShell tool. Dash Name picks the name, dash Type the record type, and dash Server the server. Dash DnsOnly rules out LLMNR and NetBIOS, and dash NoHostsFile skips the hosts file.

A quick look ahead. In this learning plan, zones live in text files on SRV01 and SRV-CORE. One server holds the primary copy, and secondaries get read-only copies by zone transfer. In Topic 4.1 you meet Active Directory-integrated zones on DC01. They are stored in the Active Directory database and copied by AD replication. They also allow secure dynamic updates, so only domain members update records. Why files now? Our servers are in a workgroup, with no domain controller yet.

Four mistakes to avoid. One: testing DNS with ping or a browser. They also use the hosts file, the cache and local name protocols. Use nslookup, or Resolve-DnsName with dash DnsOnly and dash NoHostsFile. Two: leaving test lines in the hosts file. A hosts line wins over DNS, so remove it once DNS has the record. Three: testing right after fixing a record. The old answer may be cached, so flush first. Four: reading a timeout as name does not exist. Check the server and network first.

Time to check yourself. CLIENT01 uses SRV01 as its DNS server. First: CLIENT01's hosts file gives one address for srv-core.lakeshore.test, but DNS has another. Which address does ping use? Second: ping for that name works, but nslookup fails. Why? Third: Resolve-DnsName for www.microsoft.com fails. Is that a name does not exist answer, called NXDOMAIN, and why? And fourth: SRV01 has the DNS Server role but no zones. What kind of DNS server is it? Pause the video and think it through.

Here are the answers. One: ping uses the hosts file address. Hosts lines are loaded into the resolver cache, which is checked before any DNS server. Two: nslookup asks the DNS server directly and skips the hosts file and cache. Ping used the hosts line; the DNS server has no record. Three: no. It is a timeout or server failure, because SRV01 cannot reach the root servers without internet. Four: a caching-only server. It is authoritative for nothing until you add zones.

Let me show you. On CLIENT01, in an administrator PowerShell, I add a hosts line for srv-core.lakeshore.test. ipconfig slash displaydns already lists it. I flush, and it is still there. On SRV01, I add the DNS Server role. DNS Manager shows empty zone folders, root hints and no forwarders. Back on CLIENT01, I set the DNS server to SRV01. www.microsoft.com fails with a timeout. nslookup says Server UnKnown. And srv-core answers only while the hosts file is used. With dash NoHostsFile, it times out too.

To wrap up. DNS turns names into addresses. A fully qualified domain name reads from the host up to the root. Windows checks its cache, with the hosts lines, then its DNS server, which checks zones and cache, then forwarders or root hints. Authoritative answers come from the zone; cached copies live as long as the TTL. A server with no zones is caching-only, and with no internet you get timeouts. Lab 3.1 takes about forty-five minutes and is practice only. See you there.
