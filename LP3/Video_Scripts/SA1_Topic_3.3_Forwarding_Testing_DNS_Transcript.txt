Welcome to Topic 3.3, Forwarding and Testing DNS. First you quickly rebuild your zones from Labs 3.1 and 3.2, and then your DNS servers learn to work together. You will see where a server sends a question it cannot answer, and you will add a conditional forwarder for branch.test. You will also watch a forwarder fail, because our pod has no internet. Then we build a testing toolkit and a troubleshooting flow. Last, two short concepts from the exam: DNSSEC and DNS policies.

CLIENT01 asks SRV01 for a name. First, SRV01 checks its own zones, like lakeshore.test. Next, its cache of recent answers. If neither has it, SRV01 asks another server. If the name ends in a domain with a conditional forwarder, like branch.test, it asks the server you listed, SRV-CORE. For any other name it uses its forwarders. If those fail, it falls back to root hints. In our pod only the SRV-CORE path can work, because the internet is out of reach.

A conditional forwarder covers one named domain and lives in the Conditional Forwarders node. A forwarder covers every name the server cannot answer, and you set it on the Forwarders tab in the server's properties. Root hints are the fallback: a list of the root servers at the top of DNS. Asking other servers for a client is called recursion, and you can turn it off on the Advanced tab. A stub zone is an alternative: it copies the other zone's name server records.

In DNS Manager, right-click Conditional Forwarders and choose New Conditional Forwarder. In DNS Domain, type branch.test. Under IP addresses of the master servers, click the line that says click here to add, and type SRV-CORE's address, 192.168.50.21. DNS Manager checks the address. Validated should say OK, which means SRV-CORE answered as the owner of the zone. The option to store it in Active Directory is greyed out, because SRV01 is not a domain controller. You will use it in Learning Plan 4.

Now in PowerShell. Before the change, Resolve-DnsName for app1.branch.test fails. SRV01 has no zone and no forwarder for it, and the root servers cannot be reached. Then one command, Add-DnsServerConditionalForwarderZone, with dash Name branch.test and dash MasterServers 192.168.50.21. The output shows a zone of type Forwarder. Without Active Directory, it is stored in the registry. Clear the server cache so an old failure is not reused, and then resolve the name again. Now SRV01 asks SRV-CORE for you and returns 192.168.50.21.

Now the general forwarders. Right-click SRV01, choose Properties, and open the Forwarders tab. The list holds the servers SRV01 asks for every name it cannot answer. You add or remove them with Edit. In our pod we add 8.8.8.8, a public resolver, and the check fails, because there is no internet. Below the list is a check box: Use root hints if no forwarders are available. On means try the root servers too. And notice the note: conditional forwarders win over server-level forwarders.

In PowerShell, Set-DnsServerForwarder sets the forwarder list. Set replaces the list. Get-DnsServerForwarder shows the address and the root hint setting. Now ask for www.microsoft.com, and wait. You may get a timeout after several seconds, or a quick DNS server failure. That is not a setup mistake. The pod has no internet, so nobody can answer. Meanwhile, app1.branch.test still works, because the conditional forwarder comes first. When you are done, clean up with Remove-DnsServerForwarder, because a forwarder that cannot work only slows things down.

nslookup is the classic DNS testing tool. Type nslookup alone, and you enter interactive mode. It first tells you which server it asks: here srv01.lakeshore.test. Type a name, and you get the answer. Non-authoritative answer means SRV01 got it second-hand, from SRV-CORE or from its cache. Set type equals mx asks for mail records instead of addresses. The server command switches to another DNS server, only inside nslookup. Set debug shows every detail of each reply. Type exit to leave.

Resolve-DnsName is the PowerShell way to test names, and its results are easy to filter and compare. By default it asks for A and AAAA records. Four switches matter most. Dash Type picks the record type, like MX. Dash Server skips your network setting and asks one server directly. Dash NoHostsFile skips the hosts file, so you see what DNS really says. Dash DnsOnly uses only the DNS protocol, with no LLMNR or NetBIOS fallback. It still reads the hosts file.

First, make sure the server is reachable. Test-NetConnection with dash Port 53 tries a TCP connection to the DNS port. TcpTestSucceeded True means the server is up and the firewall is open. Most queries use UDP 53, but DNS servers listen on both. Next, caches. ipconfig slash displaydns shows what the client remembers, even answers like Name does not exist. Clear-DnsClientCache empties it, the same as ipconfig slash flushdns. On the server, Clear-DnsServerCache with dash Force clears the server's cache.

When a name does not resolve, follow this flow and stop at the first failure. One: the client DNS setting. Is CLIENT01 really using 192.168.50.20? Two: is the server reachable on port 53? Three: do the zone and the record exist, spelled correctly? Four: is a forwarder set for another domain, and does its target answer? Five: caches, which can hold a saved does not exist. Six: a hosts file line that overrides DNS. Fix one thing, then test again.

Two things can mislead you. First, negative caching. If you ask for a name before it exists, the no travels back from SRV-CORE through SRV01 to CLIENT01, and each one remembers it. The DNS server keeps a negative answer for up to fifteen minutes by default. So a new record can still look missing. Clear the server cache, then the client cache, or wait. Second, the hosts file. A line there beats DNS for ping and most apps, but nslookup ignores it.

When tests are not enough, use logs. The Audit log is on by default and records changes to zones, records and settings. The Analytical log is off by default. It records one event for each query and answer, and it is light enough for most servers. Find it in Event Viewer under DNS-Server, after you choose Show Analytic and Debug Logs. Debug logging is the older way. It writes every packet to a text file, so only turn it on briefly.

DNSSEC protects answers from forgery. Signing a zone makes the server add a digital signature, an RRSIG record, next to each set of records. The data is signed, not encrypted. Two keys are used. The zone signing key signs the records, and the key signing key signs the zone's public keys. A resolver that validates holds a trust anchor, a trusted public key, and rejects answers with bad signatures. In PowerShell, Invoke-DnsServerZoneSign signs a zone. We do not sign zones in the pod.

DNS policies let one server give different answers by rule. A zone scope is a second set of records inside one zone. A policy uses criteria, like the client subnet, the server interface, the time of day or the record type, to choose the scope. A classic use is split-brain DNS: inside users get an internal address, outside users get a public one. The example adds an external scope, a record and a policy. Like DNSSEC, this is a concept only.

Four common mistakes. One: making SRV-CORE a normal forwarder just to reach branch.test. That sends every unknown name there. Use a conditional forwarder instead. Two: expecting forwarding to work both ways. SRV01 finds branch.test, but SRV-CORE needs its own forwarder for lakeshore.test. Three: trusting nslookup when ping disagrees. nslookup ignores the hosts file, so check it, and use Resolve-DnsName with dash NoHostsFile. Four: fixing a record while the error stays. The no is cached, so clear both the client and the server cache.

Time to check yourself. CLIENT01 uses SRV01 as its DNS server. First: SRV01 resolves srv01.lakeshore.test but not app1.branch.test. What do you add on SRV01? Second: you added the forwarder 8.8.8.8, and www.microsoft.com fails. Is the forwarder set up wrong? Third: nslookup says nas01 is 192.168.50.40, but ping goes to dot 99. Why? And fourth: you just added a missing record, but the client still says it does not exist. What do you do next? Pause the video and think it through.

Here are the answers. One: a conditional forwarder for branch.test, with master server 192.168.50.21, in DNS Manager or with Add-DnsServerConditionalForwarderZone. Two: no, the forwarder is fine. The pod has no internet, so neither the forwarder nor the root servers can reply, and a failure is expected. Three: there is a hosts file line on CLIENT01. ping reads it, nslookup does not. Four: a negative answer was cached. Clear-DnsClientCache on CLIENT01, and Clear-DnsServerCache on SRV01. Then test the name once again.

On SRV01, app1.branch.test fails at first. I add a conditional forwarder for branch.test pointing at SRV-CORE, and Validated says OK. After clearing the cache, the name resolves. Next, I add the forwarder 8.8.8.8, and an internet name fails, just as expected, so I remove it. On CLIENT01, nslookup shows the non-authoritative answer and the MX record. Then the negative cache: I ask for reports before it exists, add it on SRV-CORE, and it still fails until I clear both caches.

To wrap up. A server answers from its own zones and cache first, then a matching conditional forwarder, then forwarders, then root hints. With no internet, forwarders and root hints fail. nslookup asks one server directly, and Resolve-DnsName adds useful switches. When a name fails, follow the flow: setting, port 53, record, forwarding, caches, hosts file. DNSSEC signs answers, and policies choose answers. Lab 3.3 practices all of this in about fifty minutes. It is practice only. See you in the lab.
