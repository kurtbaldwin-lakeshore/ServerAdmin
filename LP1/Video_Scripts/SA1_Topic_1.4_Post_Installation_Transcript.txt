Welcome to Topic 1.4, Post-Installation Configuration. In Topic 1.3 you installed two servers. They work, but they are not ready for real jobs. They have random names, no fixed address, and the wrong time zone. In this video you will plan names and addresses, and you will learn why the clock matters. You will set everything up on SRV01 with Server Manager, and on SRV-CORE with SConfig. You will also see the PowerShell command for each task. Finally, you will check updates, activation and connectivity.

Here is the checklist for every new server. First, give it a name that follows your plan. Second, set a static IP address. Third, set the time zone and check the clock. Fourth, turn on Remote Desktop so admins can work on it from another computer. Fifth, decide how updates arrive. Sixth, check that Windows is activated. And seventh, restart so every change is applied, then verify your work. In the lab you follow it twice: in the GUI and on Server Core.

First, write down the plan. SRV01 gets 192.168.50.20, and SRV-CORE gets 192.168.50.21. Both use the subnet mask 255.255.255.0, which is the same as slash 24. The pod has no router, so there is no default gateway, and DNS stays empty until Learning Plan 3. Names use letters, numbers and hyphens, fifteen characters at most. Right now each server shows a 169.254 address. That is APIPA: Windows picks it when no DHCP server answers. Servers need a fixed address, so others can always find them.

Why fuss about time? Windows stores time in UTC and shows it in your time zone. Our pods use Central Standard Time. The bigger reason comes in Learning Plan 4. When you sign in with a domain account, Kerberos checks the time. By default, if a computer's clock is more than five minutes away from the domain controller, sign-in fails. Time also matters for logs. When servers agree on the time, you can line up their events and see what happened first.

On a Desktop Experience server, Server Manager opens when you sign in. Select Local Server on the left. The Properties tile lists the settings from our checklist. The trick is that each value on the right is a link. Select the value next to Computer name to rename the server. The Remote Desktop value opens the Remote tab. Ethernet opens Network Connections. Windows Update opens the update settings. Time zone opens Date and Time. And Product ID shows whether Windows is activated. One page, six tasks.

When you select the computer name, System Properties opens. Select Change, and you get the Computer Name slash Domain Changes dialog. Type the new name, SRV01. Leave the Workgroup setting as it is, because we join a domain later in the course. Select OK. Windows tells you that you must restart. Select OK, then Close, then Restart Now. Why restart? The name is saved right away, but Windows starts using it only after a restart. Until then, Server Manager still shows the old WIN name.

Next, the address. Select the Ethernet link, right-click the Ethernet adapter, and choose Properties. Select Internet Protocol Version 4, then Properties. Now choose Use the following IP address. Type 192.168.50.20 for SRV01. When you select the Subnet mask box, Windows fills in 255.255.255.0 for you. Leave Default gateway empty, because the pod has no router. Windows also switches DNS to Use the following DNS server addresses. Leave both of the DNS boxes empty for now. Then select OK, and then Close.

Two more dialogs. The Time zone link opens Date and Time. Select Change time zone, and pick Central Time, US and Canada, the one marked UTC minus six. Keep daylight saving checked. For Remote Desktop, the link opens the Remote tab of System Properties. Select Allow remote connections to this computer. Keep the Network Level Authentication box checked. With it, people must sign in before a session even starts, which is safer. Turning Remote Desktop on here also opens its firewall rule.

Server Core has no Server Manager window. Instead, when you sign in, SConfig opens. It is a text menu. You type a number and press Enter. The numbers you need are on the right. Two is the computer name. Eight is network settings. Nine is date and time. Seven is Remote Desktop. Five is the update setting, and six installs updates. Eleven shows activation. Thirteen restarts the server, and fifteen exits to PowerShell. If you leave SConfig, type SConfig and press Enter to come back.

On SRV-CORE, type eight. SConfig lists your network adapters. Pick index one. Then choose one, Set network adapter address. Type S for static. Type 192.168.50.21, then the subnet mask, 255.255.255.0. When it asks for a default gateway, leave it blank and press Enter. Skip DNS for now. One warning: on a server with an APIPA address, SConfig can fail with error 83, because it cannot release a DHCP lease. If that happens, go to PowerShell. Turn DHCP off with Set-NetIPInterface, remove the 169.254 address, then run New-NetIPAddress.

Every task you just saw also has a PowerShell command. Get-TimeZone shows the current zone. Setup often leaves Pacific Time. To change it, type Set-TimeZone, dash Id, and the Id in quotes: Central Standard Time. The quotes are needed because the Id has spaces. To check, put Get-TimeZone in brackets and add dot Id. Last, Rename-Computer, dash NewName SRV-CORE, dash Restart. Do the rename last. The dash Restart switch restarts the server right away, so anything after it would have to wait.

For the address, first find the adapter name with Get-NetAdapter. Here it is Ethernet, but use the name your own pod shows. Next, turn DHCP off with Set-NetIPInterface, dash Dhcp Disabled. Then run New-NetIPAddress with the interface alias, the IP address, and dash PrefixLength 24. Prefix length 24 means 255.255.255.0. There is no gateway, because our pod has no router. Get-NetIPConfiguration then shows the final result. The IPv4 address is set, and the default gateway is empty, just as planned.

Remote Desktop in PowerShell takes two steps. First, set a registry value called fDenyTSConnections to zero. That means deny connections is off. Second, enable the firewall rules in the Remote Desktop group. The GUI and SConfig do both steps for you. Now ping. Windows Server blocks it by default. To allow it, enable the rule named File and Printer Sharing, Echo Request, ICMPv4 In. We store the long name in a variable first. On Server Core, SConfig option four, then three, does the same.

Our pods have no internet, so you check updates and activation, but you do not change them. In Server Manager, use the Windows Update and Product ID links. In SConfig, option five shows the update setting: A for automatic, D for download only, and M for manual. Option eleven, then one, shows activation. Companies with servers off the internet use WSUS, Windows Server Update Services. One server downloads updates, admins approve them, and the others install them. For activation, they use KMS or AVMA.

Now prove it works. On SRV01, ipconfig slash all shows the host name, DHCP Enabled No, the new address and the mask, and an empty default gateway. Then run Test-Connection to SRV-CORE with dash Quiet, which prints just True or False. The first time you get False. Don't panic. The network is fine. Windows Server turns off the echo request rule by default, and our pod counts as a public network. Turn on response to ping on SRV-CORE, test again, and you get True.

Four common mistakes. One: renaming the server and skipping the restart. The new name only takes effect after a restart. Two: typing a gateway or DNS server just to fill the box. Leave them empty, because a wrong address causes slow lookups and strange errors later. Three: deciding the network is broken because ping fails. Remember, ping is blocked by default. Four: giving two servers the same address. Follow the plan, SRV01 is dot twenty and SRV-CORE is dot twenty-one, and check with ipconfig.

Time to check yourself. A classmate is setting up SRV-CORE. First, they renamed it in SConfig and said no to the restart. What name is it using right now? Second, which SConfig options set the static address and the time zone? Third, ipconfig on SRV-CORE shows the right address, but Test-Connection from SRV01 says False. What is the most likely cause? And fourth, why will a wrong clock matter more once we have a domain? Pause the video, think about your answers, then continue.

Here are the answers. One: it still uses the old WIN name. The new name takes effect only after a restart, which is option thirteen in SConfig. Two: option eight sets the network address, and option nine opens the Date and Time dialog for the time zone. Three: SRV-CORE blocks ping by default. Use option four, then three, to allow it, and test again. Four: domain sign-in uses Kerberos, and Kerberos rejects a clock that is more than five minutes off.

SConfig is open on SRV-CORE. I type eight and pick adapter one. See the 169.254 address? I choose one, then S for static, and type 192.168.50.21 and the mask. For the gateway I press Enter. Now nine. The Date and Time dialog opens, even on Server Core. I pick Central and select OK twice. Seven, E and one turn on Remote Desktop with NLA. Four and three allow ping. Fifteen opens PowerShell. Get-TimeZone dot Id says Central Standard Time, and Get-NetIPConfiguration shows the address. I type SConfig to go back. Last, option two, the name SRV-CORE, and Y to restart. After the restart, the menu shows SRV-CORE.

To wrap up: plan first. A name, a static address, a mask, and no gateway in our pod. On Desktop Experience, Server Manager's Local Server page is your starting point. On Server Core, SConfig does the same with numbers: two, eight, nine and seven. PowerShell can do all of it too. In Lab 1.4 you set up both servers, check updates and activation, test the connection, and record your settings. It takes about fifty minutes, practice only. See you in the lab.
