Welcome to Topic 9.3, Troubleshooting Method. All course long you have built and configured many Windows services. Now you learn how to fix them when they break, without guessing. You will use the six-step method from the CompTIA Server+ objectives. You will find the scope of a problem and ask what changed, keep a troubleshooting log, and work up the layers from the network to performance. You will match common symptoms to causes, and you will learn when to escalate.

Here are the six steps, in the words CompTIA uses. One: identify the problem and determine the scope. Two: establish a theory of probable cause, and question the obvious. Three: test the theory to determine the cause. Four: establish a plan of action to resolve the problem, and notify impacted users. Five: implement the solution or escalate. Six: verify full system functionality and, if applicable, implement preventive measures. After step six, perform a root cause analysis. And during every step, document findings, actions and outcomes. The order matters.

Step one is about facts. Ask the user exactly what happens, and write down the exact error text. Ask when it started. Then ask the most useful question in IT: what changed? Updates, new settings, a moved account, new hardware. Next, determine the scope. One user or many? One computer or all of them? One share or the whole network? The answer tells you where to look. Step one also means collecting logs, replicating the problem if you can, backing up before you change anything, and escalating if needed.

Now one ticket. CLIENT01 cannot reach srv01.sa1.lab, and step one showed that only CLIENT01 is affected. Step two, the theory: one client only, so the cause is probably on that client, maybe name resolution. Step three, the test: ping by IP address works, but by name it goes to 192.168.50.99. Step four, the plan: remove a wrong hosts file line and tell the user. Step five: delete the line and flush the cache. Step six: verify by name, the way the user works.

A troubleshooting log keeps you honest. It has seven fields. Symptom: what happens, with the exact message. Scope: who is affected and who is not. Theory: your probable cause. Test: the command you ran and its result. Action: what you changed, and when. Verify: how you proved it works. Prevent: what stops it happening again. In the example, cdiaz cannot sign in, Get-ADUser shows LockedOut True, you unlock her, she signs in, and she updates a saved password on her phone. Write the log as you go, not at the end.

Problems sit in layers, and each layer needs the layers below it. At the bottom is the physical link: is the adapter up and connected? Then IP: ipconfig and ping. Then name resolution: Resolve-DnsName, nslookup and the hosts file. Then authentication: can the account sign in? Then authorization: share, NTFS and Group Policy. Then the service itself, with Get-Service, Event Viewer and port tests. And at the top, performance. Start at the bottom, or start where the scope points. A layer that works proves every layer below it.

Here are the network tools on CLIENT01. ipconfig slash all shows the address, the mask and the DNS server. If you see 169.254 here, no DHCP server answered, and you can stop looking higher. Next, ping SRV01 by its IP address. If ping by address works but the name fails, move up to name resolution. Then Test-NetConnection with the Port parameter tests the service itself. Port 445 is SMB, file sharing. TcpTestSucceeded True means the port answers. False means the service is stopped or a firewall rule blocks it.

Name resolution has a trap. Resolve-DnsName follows the same path as your applications: the hosts file and the cache first, then DNS. Here it says 192.168.50.99. Add NoHostsFile, and it says 192.168.50.20. nslookup also says 20, because it always asks the DNS server directly. So DNS is right, and something on the client overrides it. Select-String finds the culprit: a line in the hosts file. After you remove the line, run ipconfig slash flushdns to clear the cache. Never trust nslookup alone.

When someone cannot sign in, ask the domain controller about the account. Get-ADUser with the LockedOut and PasswordExpired properties shows four things at once. Enabled False means the account is disabled. LockedOut True means too many bad passwords. PasswordExpired True means the password expired, or the account is set to change it at next logon. Search-ADAccount with LockedOut lists every locked account. And remember the clock: if a computer is more than five minutes off, Kerberos sign-in fails even with the right password.

The same fixes live on the Account tab in Active Directory Users and Computers. Open Lakeshore, Students, right-click the user, and select Properties. The Unlock account check box is available, with the currently locked out text, only while the account is locked. Tick it and select OK. Under Account options, User must change password at next logon forces a new password. Clear it if the user cannot set one. Account is disabled is further down the same list. In PowerShell, Unlock-ADAccount, Set-ADUser and Enable-ADAccount do the same jobs.

Access denied on a share means one of two gates said no: the share permission or NTFS. The stricter one wins. The Effective Access tab tells you which gate in the Access limited by column, and watch for Deny entries. Policy not applied is different. Run gpresult slash r. If a GPO is missing from the applied list, check the link, the OU and filtering. If it is filtered out, check security or WMI filtering. Then run gpupdate slash force to apply it now.

When a server is slow, find what is busy. Open Resource Monitor from Server Manager, Tools, and select the CPU tab. Select the CPU column heading to sort the processes, so the busiest one is on top. Tick its check box: the graphs add a line for that process, and the lower tables are filtered to it. Never end a process you cannot name. Right-click it for End Process, or use Stop-Process. For services, Get-Service shows Running or Stopped, and event 7036 in the System log records each stop and start.

These are general patterns from the course. A 169.254 address means the client got no DHCP answer. A name that does not resolve points to the client's DNS setting, a missing record, the hosts file or the cache. Access denied means share and NTFS together, a Deny entry or group membership. Policy not applied: check the link, OU and filtering. If the right password fails, check the clock. A full disk stops services. Remote management needs the WinRM service, the firewall and the right network profile. Treat them as theories.

Sometimes step five means escalating. Escalate when the fix needs rights or a system you do not own, when a vendor or another team must act, when many users are down or a time limit passes, or when it looks like a security incident. Change management keeps fixes safe. Write a plan with a way to undo it, get approval, back up first, notify users, and record what changed. When you escalate, hand over your log, so the next person starts where you stopped.

This topic leads into the course capstone. It is a graded skills lab at the end of Learning Plan 9. You start a pod where your instructor has planted problems from areas across the whole course. You do not know them in advance, and they are different from the ones in Lab 9.3. For each symptom you use the six steps, fix one thing at a time, verify, and write a log row. The capstone guide gives the time, the rules and how it is graded.

Four mistakes to avoid. One: changing several settings at once. Make one change, test it, and reverse it if it did not help. Two: restarting the server first. A restart can hide the cause and destroy evidence, so collect scope, logs and tests first. Three: trusting nslookup alone. It skips the hosts file and the cache, so compare with Resolve-DnsName. Four: stopping as soon as it seems to work. Verify the way the user works, and then write the log.

Time to check yourself. Use the six steps and the layers. First: only CLIENT01 has a 169.254 address, and other DHCP clients are fine. What does the scope tell you? Second: ping 192.168.50.20 works, but ping srv01.sa1.lab fails. Which layer do you test next? Third: Get-ADUser shows LockedOut True. Which step are you in, and what is the next one? Fourth: you changed two settings and the problem went away. Why is that a problem for your log? Pause the video and answer.

Here are the answers. One: the DHCP server works for everyone else, so look at CLIENT01 itself: its adapter, its network and whether DHCP is turned on. Two: the IP layer works, so test name resolution with Resolve-DnsName, nslookup, the hosts file and the DNS server setting. Three: the test confirmed your theory, so you finished step three. Step four is the plan: unlock, find the source of the bad passwords, and notify. Four: you do not know which change fixed it, so your root cause is a guess.

Let's run the method in the pod. On CLIENT01, a port test to srv01.sa1.lab fails, and the remote address is 192.168.50.99. From DC01 the same test succeeds, so the scope is just CLIENT01. My theory is name resolution on the client. Ping by IP works. Resolve-DnsName says 99, but with NoHostsFile it says 20, and so does nslookup. Select-String finds the hosts line. I back up the file, delete the line, flush the cache, and test again. It works. Last, I fill in the log.

To wrap up. Use the six steps in order, and finish with a root cause analysis. Scope and what changed come first. Log the symptom, scope, theory, test, action, verify and prevent fields as you go. Work up the layers with the right tool for each one. Make one change at a time, and escalate with your log. In Lab 9.3, about 120 minutes and practice only, you break five things on purpose, diagnose each one with the six steps, and fill in the troubleshooting log.
