Welcome to Topic 9.2, Event Logs. When something goes wrong on a server, the event logs are usually the first place to look, because Windows writes down what happened and when. In this topic you will find your way around Event Viewer and read an event properly. You will filter logs, save a custom view and choose how much history a log keeps. Then you will ask the same questions in PowerShell, create test events of your own with eventcreate, and forward events from SRV01 to a collector on DC01.

Open Event Viewer and look at the tree on the left. Windows Logs holds the classic logs. Application is for programs and services. Security holds audit events, like sign-ins and lockouts. Setup records roles, features and updates, and System is Windows itself, its drivers and services. Forwarded Events stays empty until this computer collects events from others. Under Applications and Services Logs, each role or app has its own log, such as DNS Server. Very detailed Analytic and Debug logs stay hidden until you show them from the View menu. Custom Views are saved filters.

Select an event and the General tab shows its properties. The level tells you how serious it is. The source is the program or component that wrote the event, and the Event ID is its number. Together, source and Event ID name the kind of event, because the same number can mean different things from different sources. Task Category and Keywords add detail; in the Security log the keywords say Audit Success or Audit Failure. Logged is the time, and Computer is where it happened.

There are five levels, and PowerShell uses a number for each. Critical is one: a serious failure, like a restart without a clean shutdown. Error is two: something failed, such as a service that would not start. Warning is three: not a failure yet, but worth a look. Information is four, and Verbose, five, is extra detail for debugging. When people say problems, they mean Critical, Error and Warning. The Security log is different. Success and failure there are keywords, Audit Success and Audit Failure, so that log shows a Keywords column first.

A busy log can hold thousands of events, so you filter. Select a log, then Filter Current Log in the Actions pane. Set Logged to Last 24 hours. Tick Critical, Error and Warning. You can stay with the current log or pick a source, such as SA1Lab. In the Event IDs box, type a number to show only that ID, or a minus sign and a number to leave one out. Remember, a filter only changes what you see. Nothing is deleted, and Clear Filter brings every event back.

A filter works on one log and disappears when you clear it. A custom view is a filter you keep. Select Create Custom View, tick Critical, Error and Warning, and choose two logs at once: Application and System. Save it with the name SA1 Problems. It now sits under Custom Views every time you open Event Viewer. You can export it and import it on your other servers too. Administrative Events is a built-in view that works the same way.

Four more tools. Find searches the text of the events in the current log, which is handy for a name like SA1Lab. Save All Events As writes the log to an evtx file that you can open later on any computer. Attach Task To This Event creates a scheduled task that starts a program each time that event appears. We treat it as a concept. And behind every filter is an XML query. You can see it on the filter's XML tab, and the Details tab shows one event as XML.

Right-click a log and choose Properties. Maximum log size decides how much history you keep. Then you choose what happens when the log is full. Overwrite events as needed is the default: the oldest events go first. Archive the log when full saves the full log as a file and starts a new one, so watch your disk space. Do not overwrite events sounds safe, but when the log is full, new events are simply lost until someone clears it. One more fact: clearing the Security log writes event 1102, so a cleared log leaves a trace.

Get-WinEvent does all of this from PowerShell. With ListLog you see each log's size and mode. Circular means overwrite as needed. With LogName and MaxEvents you get the newest events from one log. The most useful parameter is FilterHashtable. It is Filter Current Log written as code. Give it the log names, the levels as numbers, one, two and three for the problems, and a StartTime, here one day ago. You can also use the keys ProviderName for the source and Id for the Event ID.

To practice, it helps to have an event whose answer you already know. eventcreate writes one for you. In an administrator window, give it the type with slash T, the ID with slash ID, the log with slash L, the source with slash SO and the text with slash D. Here that is a warning, ID 900, in Application, from the source SA1Lab. A new source name is registered the first time. Two limits: IDs go from 1 to 1000, and only Application or System, never Security.

Event forwarding copies events to one collector. In the lab, SRV01 is the source and DC01 is the collector. They talk over WinRM, which is on by default, on port 5985, with Kerberos in the domain. DC01 runs the Windows Event Collector service and stores the events in Forwarded Events. In a collector-initiated subscription, DC01 lists its sources and reads their logs with its computer account. In a source-initiated subscription, Group Policy tells the sources where the collector is, and they push events. That scales to many servers.

On DC01, open Subscriptions in Event Viewer and create a subscription. Name it SA1 SRV01 Warnings. The destination log is Forwarded Events. Choose Collector initiated, then Select Computers, add SRV01 and use Test. With Select Events, choose the Application log and the levels Critical, Error and Warning. Under Advanced, keep Machine Account and pick the delivery. Normal pulls in batches and can take up to 15 minutes. Minimize Latency pushes within about 30 seconds, which is what you want in a lab.

Here are the command line steps. On SRV01, add the computer account SA1 backslash DC01 dollar to the local group Event Log Readers. Computer accounts end with a dollar sign. On DC01, run wecutil qc. It sets the Windows Event Collector service to a delayed automatic start, starts it and turns on the Forwarded Events log. wecutil gr shows the runtime status of the subscription for each source; you want Active. Last, Get-WinEvent on the ForwardedEvents log shows your event, and MachineName tells you it came from SRV01.

You have already used event logs in this course. In Lab 6.3, event 4625 on CLIENT01 recorded each failed sign-in, and event 4740 on DC01 recorded the lockout. In Lab 6.4, event 3076 in the CodeIntegrity Operational log told you App Control would have blocked a program. DHCP writes to its own DHCP-Server logs, plus the text audit log you read in Learning Plan 5, and DNS has the DNS Server log. The tools from this topic work for all of them, for example Get-WinEvent with LogName Security and Id 4740.

Many servers send their events to a central store, where they are kept longer, searched and turned into alerts. Event forwarding is the built-in way. A SIEM, short for Security Information and Event Management, collects logs from servers, firewalls and other devices, links related events and raises alerts. Azure Monitor can collect Windows events with its agent and a data collection rule. For the Server Plus exam, remember the idea: size logs, keep copies off the server, review them and alert on what matters.

Four mistakes to avoid. One: searching by Event ID alone. IDs repeat across sources, so filter by source and ID together. Two: clearing a log to make the errors go away. The cause is still there, and now the evidence is gone. Save first, then fix the cause. Three: a subscription that fails with Access denied. On the source, add the collector's computer account to Event Log Readers. Four: waiting for forwarded events with Normal delivery. That can take up to 15 minutes; use Minimize Latency in the lab.

Time to check yourself. You manage SRV01 and DC01. First: which FilterHashtable keys show Error and Warning events from System in the last day? Second: eventcreate with ID 1500 fails. Why? And can eventcreate write to the Security log? Third: DC01's subscription shows Access denied for SRV01. What is missing on SRV01? Fourth: the Application log is set to Do not overwrite events, and it is full. What happens next? Pause the video here and answer all four before you continue to the answers.

Here are the answers. One: LogName System, Level two and three, and StartTime set to Get-Date minus one day. Add level one if you want Critical too. Two: eventcreate accepts IDs from 1 to 1000 only, and it writes only to Application or System, never Security. Three: SA1 backslash DC01 dollar is not in Event Log Readers on SRV01; a collector-initiated subscription reads with DC01's computer account. Four: new events are lost until someone saves and clears the log. Overwrite as needed or archiving avoids that.

Let's see it in the pod. On SRV01 I open Event Viewer. In an administrator terminal I run eventcreate for a warning, ID 900, source SA1Lab. After a refresh, there it is in Application. I filter for problems in the last 24 hours, then save a custom view called SA1 Problems across Application and System. Get-WinEvent finds the same event by source and ID. Now I add DC01's computer account to Event Log Readers. On DC01 I run wecutil qc and create the subscription with Minimize Latency. I create one more event on SRV01, and within a minute it shows up in DC01's Forwarded Events, with SRV01 as the computer.

To wrap up. Events live in Windows Logs and in Applications and Services Logs. Source and Event ID name an event, and the level says how bad it is. Filters, custom views, and the size and retention settings help you find and keep the events that matter. Get-WinEvent with FilterHashtable asks the same questions in code, eventcreate gives you known test events, and forwarding copies events to a collector.
