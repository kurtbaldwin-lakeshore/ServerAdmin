Welcome to Topic 9.1, Performance Monitoring. Sooner or later someone will tell you the server is slow. This topic gives you the tools to answer with facts instead of guesses. You will learn why baselines matter, which counters to watch for CPU, memory, disk and network, and what the usual warning levels are. You will find a busy process with Task Manager and Resource Monitor, watch counters in Performance Monitor, record them with a data collector set, and read them from PowerShell with Get-Counter.

Why monitor at all? Because a number on its own means little. Is forty percent CPU bad? It depends on what is normal for that server. A baseline is a recording of normal, made while the server is healthy. Weeks one to four set the baseline. From week five, CPU climbs a little every week. That trend tells you the server will run out of capacity, so you can plan early. Monitoring also shows whether you keep your service level agreement, your promise to users about response time or uptime. Server+ covers baselines and SLAs too.

Every server has four subsystems to watch. The CPU runs instructions. Memory holds the programs and data in use. The disk stores everything, including the paging file. The network moves data to and from clients. They affect each other. When memory runs short, Windows moves pages of memory out to the disk. That is called paging. Now the disk is busy, disk latency rises, and the server feels slow. It looks like a disk problem, but the real cause is memory. A bottleneck is the one resource that holds back all the others.

A counter is one measurement that Windows keeps up to date. Here are seven to know. Look closer when CPU stays over about eighty to eighty-five percent for minutes. When Available MBytes falls under ten percent of RAM, memory is getting short, and under five hundred megabytes is critical. Pages per second that stays high while memory is low means paging. A disk read that takes more than twenty-five milliseconds is slow. Low percent Idle Time and a long queue mean a busy disk. Treat these as guidance from Microsoft, not hard limits, and compare with your baseline.

Task Manager is the quickest look. Press Control, Shift, Escape. On the Processes page, select the CPU or Memory column heading to sort, and the top process becomes your suspect. The Performance page shows live graphs for CPU, memory, disk and Ethernet. On the CPU page, note the number of logical processors. That matters later: a process that loops on one logical processor fills just one of them, so the total may look moderate. Remember that Task Manager shows the present moment. One look is not a baseline.

The Details page lists every process separately, with its process ID, or PID. Many processes share a name, like svchost or powershell. To tell them apart, right-click a column heading, choose Select columns, and tick Command line. Now you see the full path and the arguments each process was started with. Here, one powershell process is running a loop that counts up forever and never stops. That is your culprit. End task stops that one PID. But first find out what started it, or it may come back.

PowerShell does the same job. Get-Process, sorted by the CPU property, lists the processes that have used the most processor time. Note that CPU here is total seconds since the process started, not a percentage. To tell two powershell processes apart, ask CIM for the Win32 Process class, filtered by name, and select ProcessId and CommandLine. That is the same information as the Task Manager column. Then Stop-Process with the ID ends it, just like End task. This also works in a remote PowerShell session, where there is no Task Manager window to click.

Ending a busy process helps only until something starts it again. So ask who started it. Get-CimInstance Win32 Process gives each process a ParentProcessId. Read the parent's command line. A service host running the Schedule service means Task Scheduler started it. Look in the Task Scheduler Library, or run Get-ScheduledTask and Get-ScheduledTaskInfo for the last result. Check services and their startup type too, and startup apps. Fix the source first: Disable-ScheduledTask, or disable the service. Then end the process.

Resource Monitor goes deeper. Type resmon. It has five tabs: Overview, CPU, Memory, Disk and Network. Tick the check box next to a process, and it stays selected on every tab, so the lower tables show only that process. On the Disk tab, Disk Activity shows which files it reads and writes, with response times. On the Network tab, Listening Ports shows which process waits on which port: 3389 for Remote Desktop, 445 for SMB and 5985 for WinRM. Get-NetTCPConnection gives the same list.

For counters, open Performance Monitor. Type perfmon, then select Monitoring Tools, Performance Monitor, and the green plus. In Add Counters, expand an object such as PhysicalDisk and pick a counter. Then pick an instance. An instance is one copy of what the object measures: one disk, one processor core, one network adapter. The underscore Total instance combines them, which is a good first look. Select Add, then OK. Tick Show description whenever you are not sure what a counter means.

Performance Monitor has three views. Press Control G to switch. Line is the default and shows about one hundred seconds at one sample per second. Histogram bar shows one bar per counter. Report shows plain numbers. Under the line graph you see Last, Average, Minimum, Maximum and Duration for the counter you select in the legend. Windows Admin Center has a Performance Monitor tool too. It offers the same counters in a browser, for remote servers, with Line, Report, Min-Max and Heatmap graphs, and you can save a workspace.

Live graphs disappear when you close them. To record over time, you create a data collector set. Under User Defined, select New, Data Collector Set, give it a name such as SA1 Baseline, and choose Create manually. Pick Performance counter, add your counters, and set the sample interval. The wizard offers fifteen seconds; in the lab you use five. The root directory is C, PerfLogs, Admin, SA1 Baseline. Under System you also find two ready-made sets, System Diagnostics and System Performance. They run for about a minute.

A set with no stop condition runs until somebody stops it. So open its Properties, select the Stop Condition tab, and set an overall duration, for example five minutes. At one sample every five seconds, that is about sixty samples per counter. You can predict that number because you chose both values. Each run creates a new report under Reports, User Defined, with the computer name, the date and a run number. Open it, and you get the same graph tools, but on recorded data from the log file.

In PowerShell, Get-Counter reads counters directly. Put the counter paths in a variable, then add SampleInterval for the seconds between samples and MaxSamples for how many. Without them you get one sample, one second apart. Each sample has one timestamp and a value for every counter. For data collector sets there is a command-line tool called logman. logman create counter makes a set; dash si sets the sample interval and dash rf how long it runs. logman start runs it, and logman query shows its settings and status.

Now put the clues together. Low Available MBytes, high Pages per second and a busy disk point to memory. Find the process using the most memory, or add RAM. CPU over eighty-five percent for minutes, with one process on top, points to the CPU. Find that process and its command line. Slow disk reads with a long queue while memory is fine point to the disk. Traffic near link speed points to the network. And always check memory first, because a memory shortage makes the disk look guilty.

Four mistakes to avoid. One: judging a server from one look at Task Manager. Record a data collector set and compare it with the baseline. Two: buying faster disks when memory is short. Check Available MBytes and Pages per second first. Three: treating rules of thumb as hard limits. Short spikes are normal; look for values that stay high and differ from the baseline. Four: leaving a test running. Give every data collector set a stop condition, and stop your CPU loop when you finish the lab.

Time to check yourself. First: SRV01 has four logical processors, and one process loops on one of them. About what does percent Processor Time for the Total instance show? Second: Available MBytes is low, Pages per second is high, and a disk read takes forty milliseconds. What do you fix first? Third: a data collector set samples every five seconds and stops after five minutes. About how many samples does it record per counter? Fourth: Details shows two powershell processes. How do you tell which one runs the loop? Pause the video and answer.

Here are the answers. One: about twenty-five percent. The Total instance averages all logical processors, so one full core out of four adds about a quarter. Two: memory first. The paging is what keeps the disk busy, so more RAM, or less memory use, calms the disk too. Three: about sixty. Five minutes is three hundred seconds, divided by five. Four: add the Command line column in Details, or use Get-CimInstance. The loop's command line contains while true. Did you get all four?

Let's see it on SRV01. In Task Manager, the CPU page shows the number of logical processors. On Details, I add the Command line column. In Performance Monitor, I add processor time and Available MBytes, and switch views with Control G. Here is SA1 Baseline, already recorded, with its first report. Now I start a loop in a second PowerShell window. CPU climbs. Task Manager sorts it to the top, and the command line gives it away. Resource Monitor filters to it. Get-Counter confirms the CPU value. End task, and the CPU drops back.

To wrap up. A baseline tells you what normal is. Watch CPU, memory, disk and network together. Task Manager and Resource Monitor show the present moment. Performance Monitor and data collector sets show what happens over time. The rules of thumb are guidance, and memory is the first thing to check. In Lab 9.1, about eighty-five minutes and practice only, you use all of these tools on SRV01, record SA1 Baseline twice, once quiet and once under a CPU loop you start yourself, compare the reports, practice with a scheduled task of your own, and finish with Get-Counter.
