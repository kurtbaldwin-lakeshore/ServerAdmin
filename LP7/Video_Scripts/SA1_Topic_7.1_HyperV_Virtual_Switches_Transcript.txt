Welcome to Topic 7.1, Hyper-V and Virtual Switches. This learning plan turns one server into many. First you learn what virtualization is, and the difference between type 1 and type 2 hypervisors. You see how Hyper-V is built, with partitions and the VMBus. You check the host hardware and the license before you install anything. Then you install Hyper-V with Server Manager and PowerShell, set the host defaults, and build the three kinds of virtual switches that every later lab in this plan uses.

Picture three physical servers: one for DNS, one for DHCP, one for files. Each one sits mostly idle. Virtualization lets one physical computer run all three as virtual machines, or VMs. Each VM acts like its own computer with its own operating system. Three terms. The host is the physical computer that runs the VMs; in our pod that is HV01. A guest is a VM and the operating system inside it. And the hypervisor is the software that shares the hardware and keeps the VMs apart.

Hypervisors come in two types. A type 1 hypervisor runs directly on the hardware, which is why it is called bare metal. Hyper-V and VMware ESXi are type 1, and servers use this type. A type 2 hypervisor is an app that runs on top of a normal operating system, like VMware Workstation or VirtualBox on a desktop. Type 1 is faster and more secure, because nothing sits between it and the hardware. Yet Hyper-V is type 1 even though you install it as a Windows role. The next slide shows why.

With Hyper-V installed, the Windows hypervisor loads first, on the hardware. Then your Windows Server starts on top of it in the root partition, also called the parent partition. It is the only partition with direct access to the hardware and the real drivers. It creates a child partition for each VM. A child partition reaches devices only through the VMBus, a fast channel between partitions, or through the hypervisor. In each VM, clients called VSCs send device requests over the VMBus to VSPs in the root.

Before you install, check the hardware. You need a 64-bit processor with SLAT, second level address translation, so the processor maps VM memory itself. You need VM Monitor Mode extensions, which means Intel VT or AMD-V. Virtualization must be turned on in the BIOS or UEFI, often off by default. And hardware Data Execution Prevention must be on: the XD bit on Intel, the NX bit on AMD. Run systeminfo and look for four Yes lines. If a hypervisor is already running, you see a message saying so instead.

Remember Topic 1.2. The edition decides how many Windows Server VMs a licensed host may run. Standard edition allows two, when all physical cores are licensed. For two more, you license all the cores again. Datacenter, which our pod runs, allows unlimited Windows Server VMs on the licensed host. Like a Server Plus technician, size the host for itself plus every VM that runs at once. Plan for failure: one host now carries many servers. And guests that are not Windows Server follow their own license terms.

Installing Hyper-V starts like any other role. In Server Manager, open Manage, then Add Roles and Features. On the Server Roles page, check Hyper-V and select Add Features, so the management tools come along. Hyper-V adds three pages of its own. On Virtual Switches, select no adapter: you create the switches later, with the names the labs expect. On Migration and Default Stores, leave the defaults; you change the paths in Hyper-V Settings. On the Confirmation page, check Restart the destination server automatically if required, then select Install.

Here is the same job in PowerShell. Get-WindowsFeature with the name Hyper-V shows Available, so it is not installed yet. Then run Install-WindowsFeature with the name Hyper-V, dash IncludeManagementTools, and dash Restart. The server restarts by itself, possibly twice, because the hypervisor can only load at boot. Sign in again and run Get-WindowsFeature for Hyper-V star. Now the role, the Hyper-V module and the GUI tools all show Installed. On Server Core, that switch adds only the PowerShell module, nothing else.

Open Hyper-V Manager from the Tools menu in Server Manager. On the left you see Hyper-V Manager and the host, HV01. The middle shows the Virtual Machines list, which is empty on a new host, then Checkpoints, and a details pane at the bottom. On the right, the Actions pane holds the jobs for the host. New creates a virtual machine or a virtual hard disk. Hyper-V Settings holds host-wide defaults. And Virtual Switch Manager is where you build virtual networks. You use all three today.

Hyper-V Settings holds the host defaults. Under Virtual Hard Disks, set the folder for disk files, C colon Hyper-V Disks. Under Virtual Machines, set C colon Hyper-V VMs. Enhanced Session Mode gives you a Remote Desktop style connection to a VM, and it needs two check boxes. Under Server, Enhanced Session Mode Policy, check Allow enhanced session mode. Under User, Enhanced Session Mode, check Use enhanced session mode. Set-VMHost sets the paths and the server policy; the user setting is per user, in Hyper-V Manager only.

A virtual switch is a software network switch inside the host, and every VM adapter plugs into one. There are three types. An External switch binds to a physical network adapter, so VMs reach the real network like any server on the LAN. Think bridged networking. An Internal switch connects the VMs and the host, but not the physical network. Think host-only networking, great for a test lab. A Private switch connects only the VMs. Even the host cannot reach them.

In Virtual Switch Manager, select New virtual network switch, choose External, and select Create Virtual Switch. Name it External. Under Connection type, pick the physical adapter. The list shows the adapter's description, not its name, so match it with Get-NetAdapter first. Keep Allow management operating system to share this network adapter checked, so the host keeps its network. Leave the VLAN ID box off in the pod. When you select OK, a warning says the network may drop for a moment. Select Yes.

What happens behind the scenes? The physical adapter, Ethernet, becomes only an uplink for the switch. Because sharing is allowed, Windows adds a virtual adapter for the host, named vEthernet External,. The host's IP settings move to it. So HV01's address, 192.168.50.30, now sits on vEthernet External. An Internal switch also gives the host a vEthernet adapter; a Private switch gives none. The VLAN ID box would tag the host's traffic with a VLAN number. Use it only when the physical switch port is set up for it.

Now the PowerShell way. New-VMSwitch with dash NetAdapterName creates an external switch; naming an adapter is what makes it external. Add dash AllowManagementOS true to share it with the host. For the other two, use dash SwitchType Internal or Private. Get-VMSwitch lists all three with their types. Get-NetAdapter now shows two new host adapters, vEthernet External and vEthernet Internal. Last, New-NetIPAddress gives vEthernet Internal the address 10.10.10.1 with prefix length 24 and no gateway. VMs on the internal network use it in Lab 7.2.

Each VM gets its own virtual network adapter, plugged into one switch, and its settings live in the VM's settings under Network Adapter. You can change the switch at any time. Bandwidth management sets a minimum and a maximum, so one VM cannot hog the physical adapter. MAC address spoofing lets a VM send from other MAC addresses, which nested VMs need. DHCP guard and router guard drop DHCP or router messages from VMs that should not send them. You use them in Labs 7.2 and 7.3.

Four mistakes to avoid. One: installing Hyper-V with virtualization turned off in the firmware. Check systeminfo first, and turn on Intel VT or AMD-V in the BIOS or UEFI setup. Two: clearing Allow management operating system to share on the host's only adapter. The host loses its network, so keep it checked. Three: choosing a Private switch when the host must reach the VMs. Private connects VMs only, so use Internal. Four: leaving VM files in ProgramData. Set the default paths in Hyper-V Settings before you create the first VM.

Time to check yourself. HV01 now has Hyper-V and three switches: External, Internal and Private. First, is Hyper-V a type 1 or a type 2 hypervisor, and why? Second, a test VM must talk to HV01 but never to the real network. Which switch do you connect it to? Third, after you create the External switch, HV01's IP address sits on a new adapter. Which one, and why? And fourth, your company runs ten Windows Server VMs on one host. Which edition fits? Pause the video now.

One: type 1. The Windows hypervisor runs on the hardware, and Windows Server runs in the root partition on top of it. Two: the Internal switch. It connects the host and the VMs only. Private would cut off the host, and External reaches the real network. Three: vEthernet External. Sharing the adapter with the host creates that virtual adapter, and the IP settings move to it. Four: Datacenter, with unlimited Windows Server VMs. With Standard, you would have to license all the cores five times.

On HV01, systeminfo says a hypervisor has been detected, because HV01 itself runs inside NetLab. I note the description of the Ethernet adapter, then install Hyper-V in Server Manager, with no switch in the wizard and an automatic restart. After signing in again, I create the two folders and set them in Hyper-V Settings, along with Enhanced Session Mode. In Virtual Switch Manager I create External on the Ethernet adapter, then Internal and Private. Notice that 192.168.50.30 moved to vEthernet External. Finally, I give vEthernet Internal the address 10.10.10.1.

Hyper-V is a type 1 hypervisor, with a root partition, child partitions, and the VMBus between them. The host needs SLAT, Intel VT or AMD-V turned on in the firmware, and DEP. Datacenter gives unlimited Windows Server VMs, Standard gives two. You install the role with Server Manager or Install-WindowsFeature, then set the default paths and the Enhanced Session Mode Policy. External, Internal and Private switches build your virtual networks, and the host gets vEthernet adapters. In Lab 7.1, about 60 minutes and practice only, you build all of this on HV01.
