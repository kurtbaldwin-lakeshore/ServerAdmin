Welcome to Topic 7.3, Checkpoints and PowerShell Direct. In this topic you manage virtual machines from the Hyper-V host. You will see how a checkpoint works with AVHDX files, and how to choose between production and standard checkpoints. You will create, apply, rename and delete checkpoints, and learn why a checkpoint is not a backup. Then you run commands inside a VM with PowerShell Direct, copy files with Copy-VMFile, turn on nested virtualization, and compare two ways to team network adapters.

A checkpoint saves the state of a VM at one moment, so you can go back to it later. Here is how. VM1 already uses a differencing disk on the read-only base disk. When you take a checkpoint, Hyper-V freezes VM1 dot vhdx and creates a new differencing file with the extension avhdx. Every new write goes there. The AVHDX sits in the same folder as the VHDX. Each new checkpoint adds a link to the chain, and every link needs its parent. So never delete one of these files by hand.

Hyper-V has two checkpoint types. A production checkpoint is the default. It uses backup technology inside the guest, the Volume Shadow Copy Service in Windows, so the data on disk is consistent. It does not save memory, so after you apply it, the VM is off and boots normally. A standard checkpoint also saves the memory and device state, so the VM comes back running, open programs and all. Microsoft warns that standard checkpoints can cause data problems for servers that copy data to each other, such as domain controllers.

You set the checkpoint type for each VM. In Hyper-V Manager, right-click the VM, select Settings, and under Management select Checkpoints. Enable checkpoints is on by default. Production checkpoints is selected, and under it a check box lets Hyper-V make a standard checkpoint when a production checkpoint is not possible. You can also choose standard checkpoints. Checkpoint File Location says where the checkpoint files go. And Use automatic checkpoints makes one each time the VM starts. On Windows Server that option is off by default.

The same settings live in PowerShell. Get-VM, piped to Select-Object, shows the checkpoint type and whether automatic checkpoints are on. For VM1 you see Production and False. Set-VM with dash CheckpointType changes the type. Standard saves memory too. Production falls back to standard when it has to. ProductionOnly fails instead of falling back, and Disabled blocks checkpoints completely. Set-VM with dash AutomaticCheckpointsEnabled dollar false turns off automatic checkpoints for that VM. In the lab you only read these settings and keep VM1 on Production.

In Hyper-V Manager, select a VM and the Checkpoints pane shows its checkpoints as a tree. Each one sits under its parent. The item called Now shows where the VM runs today. To take a checkpoint, select Checkpoint in the Actions pane. When you select a checkpoint, the Actions pane offers Apply, Rename, Delete Checkpoint and Delete Checkpoint Subtree. A new checkpoint is named after the VM, with the date and time. Rename it to something useful, like Before-Change, so everyone knows why it exists.

When you apply a checkpoint, the Apply Checkpoint dialog asks what to do. Create Checkpoint and Apply first saves the current state, then goes back. That is the safe choice. Apply just goes back, and the changes since then are lost with no undo. Revert is a VM action that applies the last checkpoint. Delete Checkpoint does not lose your current data: Hyper-V merges the AVHDX into its parent and then removes the file, while the VM keeps running. Delete Checkpoint Subtree removes a checkpoint and everything after it.

In PowerShell, Checkpoint-VM takes a checkpoint, and dash SnapshotName gives it a name. Notice the old word. Checkpoints used to be called snapshots, and most cmdlet names still say snapshot. Get-VMSnapshot lists the checkpoints with their parents. Restore-VMSnapshot applies one, like Apply in Hyper-V Manager. Rename-VMSnapshot renames one, and Remove-VMSnapshot deletes one, which starts the merge. Aliases with the newer word also work, such as Get-VMCheckpoint, so you may see both in documentation. In the lab you use both Hyper-V Manager and these cmdlets.

Here is a rule worth remembering: a checkpoint is not a backup. The AVHDX files sit on the same host and the same disk as the VM, so one failed disk takes everything. A checkpoint holds only the changes since its parent, so it is useless without the chain. The files keep growing, long chains slow the disk, and old checkpoints can fill a volume. And going back in time confuses servers that replicate data. Use checkpoints for short changes, then delete them, and protect servers with real backups on other storage.

PowerShell Direct lets you run PowerShell inside a VM from its Hyper-V host. It does not use the network. It talks to the guest through Hyper-V itself, over the VMBus. So it works even if the VM has no network adapter, a wrong IP address, or a firewall that blocks remote management. The requirements: host and guest run Windows 10, Windows Server 2016 or later. You run it on the host that runs the VM, as a Hyper-V administrator. The VM must be running, and you need credentials for an account in the guest.

First, store the guest's credentials. Get-Credential with VM1 backslash Administrator opens a dialog for the password of VM1's own Administrator account, not your domain account. Invoke-Command with dash VMName runs one command or script block inside VM1 and then closes. Here, hostname returns VM1. Enter-PSSession with dash VMName starts an interactive session. The prompt changes to VM1 in square brackets, so you always know where your commands run. Exit-PSSession takes you back to the host. In the lab you first rename the guest to VM1, so this account name works.

Copy-VMFile copies a file from the host into a guest. It needs the Guest Service Interface integration service, which is off by default, so turn it on first with Enable-VMIntegrationService. Then Copy-VMFile takes the VM name, a source path on the host, and a destination path in the guest. Dash FileSource Host is required, and it is the only value, so the copy only goes from host to guest. Dash CreateFullPath creates the folder in the guest if it is missing. Then PowerShell Direct can read the file inside VM1.

Nested virtualization means running Hyper-V inside a virtual machine. Our pod is an example. HV01 is itself a VM in NetLab, and NetLab hands the processor's virtualization features through to it. HV01 could do the same for VM1. You need an Intel processor with VT-x and EPT, or a recent AMD EPYC or Ryzen with a newer host version. You turn it on while the VM is off. While Hyper-V runs inside a VM, that VM's memory stays fixed, even with Dynamic Memory. And nested VMs need MAC address spoofing or NAT to reach the network.

Here are the commands on the host. First, Stop-VM, because the processor setting cannot change while the VM runs. Then Set-VMProcessor with dash ExposeVirtualizationExtensions dollar true passes the virtualization features to the guest. Next, Get-VMNetworkAdapter piped to Set-VMNetworkAdapter with dash MacAddressSpoofing On lets frames from nested VMs pass through VM1's adapter. Get-VMProcessor confirms the setting is True. Then start the VM. The next step would be installing Hyper-V inside VM1, but that needs more memory than our host can spare.

A host with one network adapter is a single point of failure. Teaming joins several adapters, so traffic continues if one fails. For Hyper-V hosts, Microsoft uses Switch Embedded Teaming, or SET, which is built into the Hyper-V switch. It takes up to eight identical adapters and works in switch independent mode. The older LBFO NIC Teaming from Server Manager is deprecated for Hyper-V. From Windows Server 2022 on, binding a Hyper-V switch to an LBFO team is blocked by default. You create a SET switch with New-VMSwitch, two adapter names, and dash EnableEmbeddedTeaming dollar true. HV01 has one adapter, so this stays a concept.

Four mistakes to avoid. One: keeping checkpoints as the only backup. Back up to other storage, and delete each checkpoint once the change is tested. Two: deleting AVHDX files in File Explorer. Delete checkpoints in Hyper-V Manager or with Remove-VMSnapshot, so Hyper-V merges them. Three: PowerShell Direct with the wrong credentials or a stopped VM. Run it on the host, start the VM, and use the guest's account. Four: exposing virtualization on a running VM, or forgetting the network for nested VMs. Stop the VM first, then turn on MAC address spoofing.

Let's sum up. A checkpoint freezes the disk, and new writes go to an AVHDX file. Production checkpoints are the default and use VSS; standard checkpoints save memory too. Deleting a checkpoint merges its AVHDX, and a checkpoint is never a backup. PowerShell Direct uses dash VMName and the guest's credentials, with no network needed. Copy-VMFile needs the Guest Service Interface. For nested virtualization, expose the extensions with the VM off, and team Hyper-V adapters with SET. In Lab 7.3, about 75 minutes and practice only, you do all of this on HV01.
