Welcome to Topic 2.3, Remote Management. So far you have worked at each server's own console. Real admins rarely do that. You will learn why we manage servers remotely, and how in a workgroup. You will prepare SRV01 with a TrustedHosts list, add SRV-CORE to Server Manager, and run commands on it with PowerShell remoting. Then you will turn on OpenSSH Server and connect with ssh. Finally, you will use Remote Desktop and learn to pick the right tool for each job.

Picture one seat, say SRV01 or CLIENT01, with arrows to every other server. The servers stay in their racks or run as VMs. There are three good reasons for this. First, one console can manage many servers. Server Manager, PowerShell and Windows Admin Center all work that way. Second, Server Core has no desktop, so remote tools give it a GUI or a full PowerShell. Third, fewer visits to the console means better physical security and fewer accidents in the server room.

Here is the catch. All the computers are in a workgroup, so there is no Kerberos. In a domain, Kerberos proves who both computers are, and you just use names. Without it, Windows falls back to NTLM, and it will only send your credentials to computers you trust. So on SRV01, the computer you manage from, you list SRV-CORE in TrustedHosts. You also pass SRV-CORE's own Administrator account each time. The good news: remote management is on by default and answers the local subnet, so the firewall needs no change.

Two quick jobs on SRV01. First, name lookup. Without DNS, name lookup is not reliable, and Server Manager works best with a name rather than an IP address. So you open the hosts file in Notepad and add one line: the address 192.168.50.21, some spaces, and the name SRV-CORE. Test-Connection by name should now say True. Second, TrustedHosts. Read the list first. Then use Set-Item with the value SRV-CORE, dash Concatenate and dash Force. Concatenate adds instead of replacing. Read the value back to check it. SRV-CORE itself needs nothing.

Now Server Manager. Select Manage, then Add Servers. The dialog has three tabs: Active Directory, DNS and Import. Active Directory only helps in a domain, so in the pod you use the DNS tab. Type SRV-CORE in the search box and select Search. Our hosts file line lets it find 192.168.50.21. Select the server, then use the arrow button to move it to the Selected list. Select OK, and SRV-CORE joins the server pool. From now on, SRV01's Server Manager watches both servers.

Select All Servers, and look at the Manageability column. If both Administrator accounts have the same password, SRV-CORE already says Online. If not, you see an access error, because Server Manager tried SRV01's own account. Either way, right-click SRV-CORE and choose Manage As. Type SRV-CORE backslash Administrator, and the password shown in your pod. That name means the Administrator account that lives on SRV-CORE. That makes the credentials explicit. Select Refresh, and the status shows Online. Server Manager keeps them on SRV01.

Server Manager talks to SRV-CORE over WinRM, and PowerShell remoting uses the same connection. First, run Get-Credential with SRV-CORE backslash Administrator, and store the result in a variable called cred. Then run Enter-PSSession, dash ComputerName SRV-CORE, dash Credential, and the variable. Watch the prompt. It now starts with SRV-CORE in square brackets. Everything you type runs on SRV-CORE. Here, hostname proves it, and Get-Service shows that sshd is installed but stopped. Exit-PSSession, or just exit, takes you home to SRV01 again.

Sometimes you need just one answer, not a whole session. That is Invoke-Command. You give it the computer name, the credential, and a script block in curly braces. The script block runs on SRV-CORE, and the result comes back to your own prompt. You never leave SRV01. Ask for hostname, or for the time zone Id, and you see the answer at once. Add more names, and one command reaches many servers. Many cmdlets, like Install-WindowsFeature, also take dash ComputerName. That is what Server Manager does behind the scenes.

Next, SSH. Starting with Windows Server 2025, OpenSSH Server is installed by default. It is just not running. On a Desktop Experience server, Server Manager's Local Server page has a new line called Remote SSH Access. Select it to enable the service. The service name is sshd, it listens on TCP port 22, and its firewall rule is called OpenSSH Server In TCP. SRV-CORE has no Server Manager window, so we use PowerShell. Older servers add it as an optional feature.

On SRV-CORE, use option fifteen in SConfig to reach PowerShell. Set the startup type first. Set-Service, dash Name sshd, dash StartupType Automatic. Why first? A service whose startup type is Disabled cannot start at all, so order matters here. Then Start-Service sshd. No output means it worked. Get-Service with Select-Object shows Running and Automatic, so it will come back after a restart. Last, check the firewall rule with Get-NetFirewallRule. It should show Enabled True, so port 22 is open. If the rule is missing, create it as the lab shows.

Now go to CLIENT01 and open PowerShell. Type ssh administrator at 192.168.50.21. The first time, ssh says it cannot establish the authenticity of the host, and shows a key fingerprint. Type yes, and CLIENT01 saves that key. Then type the password. Nothing shows while you type, and that is on purpose. Look at the prompt. There is no PS in front, because the default shell is cmd. You can type powershell, or set a registry value called DefaultShell on the server, which you will do in the lab.

Remote Desktop has been on since Lab 1.4. On the Remote tab of System Properties, Allow remote connections is selected, and that also opened the firewall rules for TCP port 3389. Keep Network Level Authentication on. With it, you sign in before a session starts, so attackers do not even get a sign-in screen. Who may connect? Members of Administrators, plus members of the Remote Desktop Users group. Select Users adds people to that group. Right now Get-LocalGroupMember shows it is empty.

On CLIENT01, type mstsc to open Remote Desktop Connection. In the Computer box, type SRV01's address, 192.168.50.20. A name will work once we have DNS. Select Connect. In a workgroup, sign in as SRV01 backslash Administrator, not as CLIENT01 backslash student. You will see a warning that the identity of the remote computer cannot be verified. SRV01 uses a self-signed certificate, so select Yes in the pod. mstsc also takes options, like slash v for the computer, slash f for full screen, and slash admin.

When you finish, how do you leave? If you close the window with the X, you only disconnect. Your session keeps running on the server, with every program still open. If you select Start, your user icon, and Sign out, the session ends, programs close, and the memory is freed. Forgotten sessions can block a colleague. Remote Desktop to Server Core shows the console window, and SConfig opens, unless you take over a session that is already open. Option twelve in SConfig, or logoff, signs you out.

So which tool when? Server Manager uses WinRM on port 5985 and is great for watching many servers and adding roles. Windows Admin Center runs in a browser, talking HTTPS to the gateway on SRV01, and gives Server Core a web GUI. PowerShell remoting also uses WinRM, and is best for commands on one or many servers. SSH uses port 22 and works from any operating system. Remote Desktop uses port 3389 for a full desktop. Many servers? PowerShell. Only a desktop? Remote Desktop.

Four mistakes to avoid. One: setting TrustedHosts on SRV-CORE. The list belongs on SRV01, the computer you manage from. Two: using the wrong account with Manage As, like CLIENT01 backslash student or SRV01 backslash Administrator. Use the target's own account, SRV-CORE backslash Administrator. Three: Start-Service sshd fails. If the startup type is Disabled, Start-Service fails, so set it to Automatic first. Four: closing the Remote Desktop window and thinking you are done. That only disconnects you. Sign out so the session really ends.

Time to check yourself. You manage the pod from SRV01 and CLIENT01. First, Enter-PSSession to SRV-CORE fails with a TrustedHosts error. Which computer do you fix, and how? Second, your prompt shows SRV-CORE in square brackets. Where does Get-Service run? Third, ssh connects, but the prompt has no PS in front. Why, and how do you get PowerShell? And fourth, a help-desk user needs Remote Desktop to SRV01 but must not be an administrator. What do you do? Pause the video and think it through.

Here are the answers. One: fix SRV01, the computer you manage from. Use Set-Item on the TrustedHosts path with the value SRV-CORE, then pass dash Credential. Two: it runs on SRV-CORE. The prefix in square brackets means every command runs there until you type Exit-PSSession. Three: the default SSH shell is cmd. Type powershell, or set the DefaultShell value in the OpenSSH registry key. Four: add the user to Remote Desktop Users, with Select Users on the Remote tab. They do not need to be an administrator.

On SRV01, I add the SRV-CORE line to the hosts file, and the ping by name says True. I add SRV-CORE to TrustedHosts with Concatenate. In Server Manager I add SRV-CORE from the DNS tab. If it shows an access error, use Manage As; either way, setting Manage As to SRV-CORE backslash Administrator makes the credentials explicit. I refresh, and it is Online. In a session on SRV-CORE, I set sshd to Automatic and start it. On CLIENT01, ssh asks about the key, I say yes, type the password, and I am in. Last, Remote Desktop to SRV01, then sign out.

To wrap up. In a workgroup, remote management needs three things: name lookup, SRV-CORE in TrustedHosts on SRV01, and the target's own credentials. Server Manager adds servers with Add Servers and Manage As. Enter-PSSession gives you a session, and Invoke-Command runs one command. OpenSSH comes with Server 2025: start sshd, and use port 22. For Remote Desktop, keep NLA on, use Remote Desktop Users, and sign out. Lab 2.3 practices all of this in about fifty minutes. It is practice only. See you in the lab.
