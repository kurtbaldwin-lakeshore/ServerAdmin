Welcome to Topic 2.2, Windows Admin Center. So far you have managed each server at its own console, with Server Manager or SConfig. Now you get one web page that manages many servers at once. In this video you will learn how the gateway works and where you can install it. You will walk through the installer and its certificate choice. You will sign in, add servers, and handle the extra steps a workgroup needs. Then you will tour the tools for a server, and finish with how to protect the gateway.

Windows Admin Center is a free tool set that runs in your browser. Your browser, Edge or Chrome, talks HTTPS to a gateway. In our pod the gateway is SRV01. The gateway then talks to each managed server over WinRM, Windows Remote Management, and runs PowerShell and WMI commands there. That gives you three big wins. You install nothing on your own PC. The managed servers need nothing extra, because Windows Server already has WinRM. And Server Core, which has no desktop tools, finally gets a graphical tool from afar.

You can install Windows Admin Center in four ways. On a Windows 11 PC, it is a local client: just for you, at localhost port 6600. On Windows Server it becomes a gateway that many admins share, on port 443. It can also go on a managed server, or on a failover cluster that keeps it running. In our pod we use a gateway on SRV01, so the address is https colon slash slash SRV01. Two rules from Microsoft: never install it on a domain controller, and use Edge or Chrome.

The installer is a short wizard. After the welcome page you accept the license terms, and then you pick an installation mode. Express setup chooses the network access and port for your operating system. On Windows Server, that means remote access on port 443. That is what you use in the lab. Custom setup lets you choose every setting yourself: local or remote access, the port numbers, the certificate and its thumbprint, the full domain name, trusted hosts mode, and WinRM over HTTPS. After that come the certificate, updates, diagnostic data, and Ready to install.

Next the wizard asks for a TLS certificate. TLS is what puts the S in HTTPS. It encrypts the traffic and proves the server's identity. You have two choices. In production, you use a certificate you already installed, issued by a trusted certificate authority for server authentication. In a lab, you let the installer generate a self-signed certificate. It works, but it expires after sixty days, and browsers warn about it because no authority vouches for it. Then you choose update and diagnostic settings, select Install, and finish with Start Windows Admin Center selected.

Server Core has no wizard, so Microsoft shows a silent install with PowerShell. First list C colon Install to find the installer's name. Then run Start-Process with the argument slash VERYSILENT and dash Wait. It installs with the default settings and shows no pages. Next, Get-Service WindowsAdminCenter should say Running. If it says Stopped, use Start-Service. Last, Test-NetConnection to SRV01 on port 443. TcpTestSucceeded True means the gateway is listening for browsers. You run both checks in the lab too.

Now open Edge and go to https colon slash slash SRV01. Because the certificate is self-signed, Edge says Your connection isn't private. In this lab that warning is expected, and you trust the server on purpose, because you built it. Select Advanced, then Continue to srv01. Never do that on a site you do not own. Next comes the Windows Admin Center sign-in page. In the pod you sign in as SRV01 backslash Administrator with the password shown in your NetLab pod. If Edge asks you to select a certificate, select OK.

After you sign in, you land on All connections. This is your list of everything the gateway manages. The plus Add button adds a server, a Windows PC, a cluster or an Azure VM. Manage as sets which account the gateway uses for a selected connection. And the Managing As column shows that account for each row. By default Windows Admin Center uses single sign-on: it tries the account you signed in with. In a workgroup, that account only exists on SRV01, so SRV-CORE needs its own credentials.

To add a server, select plus Add, then Add under Servers. On the Add one tab, type the server name. Our pod has no DNS server until Learning Plan 3, so type the IP address, 192.168.50.21. It always works. Select Add. Now the credentials. Select the connection and choose Manage as. Type the account as SRV-CORE backslash Administrator and its password. The computer name in front tells Windows whose account it is. Both servers have an Administrator, but in a workgroup they are two different accounts.

There is one more workgroup rule. Without a domain there is no Kerberos to prove who a server is. So WinRM only sends your credentials to computers on a list called TrustedHosts. The gateway is the one connecting, so the list that matters is on SRV01. First look at it with Get-Item. Express setup lets Windows Admin Center manage this list, so you may see a star. If it is empty, use Set-Item with the name and the address. Careful: Set-Item replaces the whole list, so save the old value first.

Select a server and it opens on the Overview tool. On the left is the Tools pane, with a search box at the top. Type a few letters to jump to a tool. Overview shows the computer name, the operating system, memory, up time and live charts for CPU, memory and network. Its toolbar has Restart and Shutdown, so be careful. Further down the pane you find PowerShell, which gives you a remote PowerShell session right inside the browser. The pane scrolls, and there are many more tools below.

Here are the main tools Microsoft lists for a server connection. You will recognize many of them from the Windows desktop: Certificates, Devices, Events, Firewall, Local users and groups, Registry, Services, Storage, Updates and more. The highlighted ones are the five you use in the lab: Overview, Roles and features, Services, Events and PowerShell. Some tools only show up when the server has that role, such as DNS, DHCP or Virtual machines. And the gear in the top corner opens the gateway settings, including Extensions.

Everything the gateway does, you can also do with PowerShell over WinRM. First, Get-Credential asks once for SRV-CORE backslash Administrator, and you keep it in a variable called cred. Install-WindowsFeature with dash ComputerName and dash Credential installs Windows Server Backup on SRV-CORE, just like the Roles and features tool. Then Invoke-Command runs any command on the remote server, such as Get-Service for the services or Get-WinEvent for the event logs. That is really what the gateway does for you, quietly, behind the scenes.

Windows Admin Center is built from extensions. In fact every tool and every connection type is one. Under Settings, then Extensions, you see available extensions, installed extensions and feeds. Select one and choose Install, and the page reloads. The default feed lives on the internet, so in a closed network an admin adds a file share or folder as a feed. Windows Admin Center can also run inside the Azure portal, in preview, for Azure VMs and Arc-enabled servers. It needs no inbound port. You meet Azure Arc in Server Administration 2.

A gateway is a high-value system, because it can reach every server it manages. Keep it patched and limit who signs in. Use a trusted certificate in production, never the sixty-day self-signed one. Windows Admin Center has two roles for its own access. Gateway users can manage servers through it. Gateway administrators can also decide who gets in and how they sign in. But remember the two separate doors. Getting into the gateway does not open the servers. You still need administrator credentials on each server.

Four common mistakes. One: installing the gateway on a domain controller. That is not supported, so use a member server or a Windows 11 PC. Two: using the SRV01 Administrator account for SRV-CORE in a workgroup. Use the target's own account, SRV-CORE backslash Administrator. Three: setting TrustedHosts and wiping out the old list. Read it first and save it, because Set-Item replaces everything. And four: keeping the self-signed certificate in production. It expires after sixty days and trains people to ignore warnings.

Time to check yourself. Imagine you run the gateway on SRV01. First, which protocol does the gateway use to manage SRV-CORE, and what must you install on SRV-CORE first? Second, Edge shows a certificate warning at https SRV01. Why, and what fixes it for good? Third, adding SRV-CORE fails with your SRV01 account. What do you change? And fourth, a help desk worker can sign in to the gateway. Can they manage every server? Pause the video now, think about your answers, and then continue.

Here are the answers. One: WinRM, running PowerShell and WMI. You install nothing extra, because Windows Server already has WinRM turned on. Two: the certificate is self-signed, so no authority vouches for it. A certificate from a trusted authority fixes it for good. Three: use SRV-CORE backslash Administrator, the target's own account, and check TrustedHosts on the gateway. Four: no. Access to the gateway is not access to the servers. The worker still needs administrator credentials on each server they want to manage, and those come from each server, not from the gateway.

I am at the SRV01 console. I run the installer from C colon Install. I accept the terms, pick Express setup, and a self-signed certificate. Install, Finish, and Edge opens. I type https SRV01, select Advanced and Continue, and sign in as SRV01 Administrator. In PowerShell I read TrustedHosts. A star means the gateway trusts all hosts. Back in the browser: plus Add, Servers, and the address 192.168.50.21. Then Manage as, with SRV-CORE backslash Administrator. Here is the Overview. In Roles and features I install Windows Server Backup. Services shows WinRM running. In the PowerShell tool, hostname answers SRV-CORE.

To wrap up: your browser talks HTTPS to the gateway, and the gateway talks WinRM to the servers. On Windows Server the gateway uses port 443. A self-signed certificate is for labs only and lasts sixty days. In a workgroup, use the target's own account and check TrustedHosts. Protect the gateway, and remember that gateway access is not server access. In Lab 2.2 you install the gateway, add SRV01 and SRV-CORE, and manage SRV-CORE with five tools. It takes about forty-five minutes, practice only. See you in the lab.
