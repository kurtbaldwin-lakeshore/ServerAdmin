Welcome to Topic 8.3, File Shares and Permissions. A file server is only useful when the right people can reach the right files, and nobody else can. In this topic you will meet SMB, the protocol behind Windows file shares. You will share a folder three ways: Advanced Sharing, Server Manager and PowerShell. You will set share permissions and NTFS permissions, and work out what happens when the two combine. Then you will check access with Effective Access and icacls, and compare SRV01 with the NAS in your pod.

SMB stands for Server Message Block. When you type backslash backslash SRV01 backslash Projects, that is a UNC path, and SMB carries the conversation. SMB 1.0 is old and unsafe. Windows Server 2019 and later and Windows 11 do not install it, and you should never add it back. SMB 2 replaced it from 2007, and SMB 3 is what you use today. Signing proves who sent each message and that nobody changed it. Windows 11 24H2 requires it both ways, and Windows Server 2025 requires it for connections it opens. Encryption is optional and off by default.

A share has its own short permission list with only three levels. Read lets people see names, open files and run programs. Change adds create, edit and delete. Full Control adds changing NTFS permissions and taking ownership. Remember one thing: share permissions are checked only when someone comes through the share over the network. Someone signed in at the server itself never meets them. So the common practice is simple. Give Authenticated Users Change, or Full Control, at the share, and do the real control in NTFS. Advanced Sharing starts with Everyone Read, so you swap that entry.

Here is the classic way. In File Explorer, open the folder's Properties, the Sharing tab, and Advanced Sharing. Tick Share this folder. The share name defaults to the folder name, Projects. Then select Permissions. In Permissions for Projects you see Everyone with Read. Remove it, select Add, type Authenticated Users and check the name. Then tick Allow Change. Read is ticked along with it. Leave every Deny box clear. Select OK twice, and the folder is shared. Nothing about NTFS has changed yet. That comes next.

Server Manager has a wizard too. In File and Storage Services, open Shares, then Tasks, New Share. First you pick a profile. SMB Share Quick works for any folder and is the one you would use here. SMB Share Advanced adds quotas and needs File Server Resource Manager, which is Topic 8.4. The Other Settings page holds a key option: Enable access-based enumeration, or ABE. With ABE, users see only the files and folders they can access. dpatel will not even see Faculty-Only. But ABE only hides things. NTFS still decides who gets in.

In PowerShell, New-SmbShare does it in one command. Give the name and path, then ChangeAccess for Authenticated Users, and FolderEnumerationMode AccessBased to turn on ABE. Because you name the access yourself, there is no Everyone entry to remove. Get-SmbShareAccess lists the share permissions, one row per entry. To change a right, revoke the entry with Revoke-SmbShareAccess, then add it again with Grant-SmbShareAccess and the new right: Full, Change or Read. The Force switch skips the confirmation question.

NTFS permissions live on the files and folders themselves, so they work over the network and locally. The basic permissions are Full control, Modify, Read and execute, List folder contents, Read and Write. Modify is the everyday permission for people who edit files; it includes delete but not changing permissions. Each basic permission is really a bundle of advanced permissions, such as Create files, Delete or Change permissions. And permissions add up: a user gets every Allow entry for the user and every group the user is in.

Permissions flow down. A new folder inherits entries from its parent, and C colon backslash gives the Users group Read and execute. So on Projects you disable inheritance and set explicit entries: GG-Faculty Modify and GG-Students Read and execute. Faculty-Only does the same, without students. When entries disagree, explicit Deny wins first, then explicit Allow, then inherited Deny, then inherited Allow. Use Deny rarely. It hits every member of a group. Removing an entry is cleaner.

This is where you do it. Open the folder's Properties, the Security tab, and Advanced. The list shows Type, Principal, Access, Inherited from and Applies to. Every entry here comes from C colon backslash, including two for Users. Select Disable inheritance. Windows asks what to do with the inherited entries. Choose Convert: they stay as explicit copies, so nothing breaks. The other choice removes them all and leaves an empty list. After converting, remove the Users entries and add the GG groups.

Now the most important rule in this topic. A user on CLIENT01 who opens backslash backslash SRV01 backslash Projects passes two gates. First the share permissions, then NTFS. Work out each gate on its own, then take the lower result. cdiaz has Change at the share and Modify in NTFS, so she can create, edit and delete. dpatel has Change at the share but only Read and execute in NTFS, so he can only read. If you set the share to Read, cdiaz can only read too. At the server's own console, only NTFS counts.

Remember AGDLP from Learning Plan 4. Accounts go into global groups, global groups go into domain local groups, and the domain local group gets the permission. DL-Shared-Read is an example: it holds GG-Faculty and GG-Students, and it got Read on C colon backslash Shared in Lab 6.2. In Lab 8.3 you take a shortcut and give the GG groups the NTFS entries directly. In one small domain that is fine. The full AGDLP way would use groups such as DL-Projects-Modify and DL-Projects-Read, so a new group needs only a membership.

How do you know what someone can really do? Use the Effective Access tab in Advanced Security Settings. Choose Select a user, type cdiaz, and select View effective access. Windows adds up every entry for her and all her groups. Each permission gets a green check or a red X. For cdiaz on Projects you see read, write and delete allowed, but Full control, Change permissions and Take ownership denied. The Access limited by column tells you which gate said no: file permissions or the share. The tab never changes anything.

icacls shows the same list as text. OI and CI mean files and subfolders inherit the entry. M is Modify, RX is Read and execute, F is Full control. CREATOR OWNER has IO, inherit only. It is a template, not a real user. When cdiaz creates Plan dot txt over the share, she becomes the owner, and Windows turns that template into an entry for her: Full control, marked I for inherited. So she can change permissions on her own file, while other faculty only have Modify. Get-Acl shows the owner.

Run Get-SmbShare on any server and you see shares you never made. C dollar for each drive, ADMIN dollar for the Windows folder, and IPC dollar for remote management. Windows creates them itself. The dollar sign hides a share from browse lists, and only administrators can use C dollar and ADMIN dollar. Leave them in place; remote tools depend on them. Offline files is the other idea here. The share's caching setting lets a laptop keep working when the server is out of reach, then sync later. The default lets users pick the files.

Your pod has a second file server, NAS01, running TrueNAS. A NAS is an appliance managed from a web page. It also speaks SMB, so users see a share just like on SRV01. The difference is identity. NAS01 is not in the domain, so it uses its own local account, nasuser. SRV01 uses Active Directory groups, NTFS, ABE and Effective Access. To connect, type net use, the drive letter, the path, slash user colon NAS01 backslash nasuser, and a star. Name NAS01 in front, because otherwise Windows sends your domain, SA1, and the NAS only knows its own local account. The star makes Windows ask for the password, so it never appears on the command line.

Four mistakes to avoid. One: locking down the share but leaving Users Read and execute in NTFS. Every domain user can still read through the share. Disable inheritance and remove Users. Two: adding Deny for students on Faculty-Only. Just remove their entry. Three: choosing Remove all inherited permissions instead of Convert. The folder ends up with no entries at all. Four: testing only as Administrator. Administrators can open almost anything. Sign in as cdiaz and dpatel, and check the Effective Access tab for each.

Check yourself. Projects has the share permission Authenticated Users Change, NTFS GG-Faculty Modify and GG-Students Read and execute, and ABE is on. First: the share is changed to Read. What can cdiaz do over the network, and at SRV01 itself? Second: dpatel does not see Faculty-Only. Why, and what happens if he types the full path? Third: why does cdiaz have Full control on Plan dot txt? Fourth: can dpatel save a new file in Projects, and which gate stops him? Pause and answer.

Here are the answers. One: read only over the network, because the most restrictive gate wins. At SRV01 there is no share, so she keeps Modify. Two: dpatel has no entry on Faculty-Only, so ABE hides it, and if he types the path, NTFS gives access denied. Three: she created the file, so she owns it, and the CREATOR OWNER entry became Full control for her. Four: no. The share allows Change, but NTFS gives GG-Students only Read and execute.

Let's do it in the pod. On SRV01 I create the Projects folder, and icacls shows the Users entries it inherited. I share it with Advanced Sharing, remove Everyone and give Authenticated Users Change. In Server Manager I turn on access-based enumeration. In Advanced Security Settings I disable inheritance, convert, remove Users and add the two GG groups. Faculty-Only gets its own list without students. Effective Access confirms dpatel has nothing there. On CLIENT01, cdiaz creates a file. dpatel cannot see Faculty-Only and cannot write.

To wrap up. Use SMB 3 with signing, and keep SMB 1.0 off. Share permissions have three levels: Full Control, Change and Read. NTFS permissions use inheritance, explicit entries and, rarely, Deny. Over the network the most restrictive gate wins. Check the result with Effective Access, ABE and icacls.
