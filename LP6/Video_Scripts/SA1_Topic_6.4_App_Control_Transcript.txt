Welcome to Topic 6.4, App Control for Business. Now you control which programs may run at all. You will learn the difference between an allow list and a block list, and when to pick App Control or AppLocker. You will read a policy file and start from an example policy that ships with Windows. You will meet policy formats, deploy a policy with CiTool or Group Policy, read the audit events, and remove a policy safely, all in audit mode.

There are two ways to control applications. A block list allows everything except the files you name. Brand new malware is not on the list yet, so it runs. An allow list works the other way around. Only files the policy trusts may run, so unknown code is stopped. When a program starts, Windows asks: does a rule trust it? If yes, it runs. If no, an enforced policy blocks it and logs event 3077. In audit mode it still runs, and Windows logs event 3076 instead.

Windows has two application control technologies. App Control for Business arrived with Windows 10. Its old name was Windows Defender Application Control. Microsoft services it as a security feature, it covers kernel drivers, and it keeps getting new features. Its policies apply to the whole device and every user. AppLocker is older, from Windows 7. It only gets security fixes, but it can target specific users and groups. So the rule of thumb: use App Control where you can, and add AppLocker when different people on a shared PC need different rules.

An App Control policy is an XML file. At the top you see the PolicyID and the BasePolicyID. They are GUIDs, long unique numbers, and for a base policy both hold the same GUID. Next comes the Rules section. These are rule options, switches for the whole policy, such as Enabled colon Audit Mode. Then come the file rules and signers. They say which files or publishers are trusted, or denied. Near the end, the Settings section holds the friendly name that tools like CiTool show. PowerShell cmdlets edit it for you.

Rule options have numbers. Option 0, Enabled colon UMCI, means the policy also checks user-mode programs, not only drivers. Option 3, Enabled colon Audit Mode, is the one to remember: it logs what would be blocked, and blocks nothing. Option 6 lets the policy file itself stay unsigned. Option 11 turns off checks of scripts. Option 16 lets later policy updates apply without a restart, and option 17 lets a base policy accept supplemental policies. Set-RuleOption with dash Option 3 adds audit mode; adding dash Delete removes it, which enforces the policy.

A rule level is how a rule recognizes a file. Hash trusts the exact file contents. Every update needs a new rule. FilePath trusts a folder or path. Use it only for admin-only folders. At run time App Control ignores a path rule for a folder that normal users can write to, like C colon Users Public. Publisher trusts a signing certificate and company name, so all of that company's signed software. FilePublisher narrows it to one file name and a minimum version. New-CIPolicy picks levels with dash Level and dash Fallback.

Windows ships example policies in C colon Windows, schemas, CodeIntegrity, ExamplePolicies. DefaultWindows comes in an audit and an enforced version. It allows Windows itself, kernel drivers and Store apps, and it is our lab policy. AllowMicrosoft adds apps signed by Microsoft, like Office. AllowAll allows everything, the starting point for a block list. There is also an example supplemental policy for DefaultWindows. Microsoft also offers a graphical App Control Wizard, but it is a download, and our pod has no internet.

Policies come in two formats. The old single policy format allows one policy per computer, in a file called SiPolicy dot p7b. The multiple policy format, from Windows 10 1903 and in Windows 11, lets many policies work side by side, each in a file named after its policy ID, dot cip. Two base policies form an intersection: a file must pass both. A supplemental policy adds trust to a base: a file passes either one. The base needs option 17 for that. Set-CIPolicyIdInfo links a supplemental to its base, and Merge-CIPolicy joins rules.

Here are the first lab commands on CLIENT01. Make a folder, C colon AppControl, and copy DefaultWindows underscore Audit dot xml into it as SA1 underscore Audit dot xml. Then Set-CIPolicyIdInfo with dash ResetPolicyID gives the copy its own unique ID and puts it in multiple policy format. Dash PolicyName sets the friendly name, SA1 Audit CLIENT01. Set-RuleOption with dash Option 3 makes sure audit mode is on. Finally, list the rule options and check that audit mode is there.

How does a policy reach a computer? CiTool, with dash dash update-policy, is built into Windows 11 22H2 and later and Windows Server 2025. Group Policy has a setting called Deploy App Control for Business, but it supports only the single policy format, and a restart applies it. Intune uses a configuration service provider that handles multiple policies without a restart. Our policy is in multiple policy format, so CLIENT01 uses CiTool. You still learn where the Group Policy setting lives.

Windows loads a binary file, not the XML. First, read the policy ID from the XML into a variable. The binary file name is that ID with the extension dot cip. ConvertFrom-CIPolicy turns the XML into that binary. Then CiTool dash dash update-policy deploys it, and it needs administrator rights. To check, run CiTool dash lp with dash json, convert the JSON, and filter on the friendly name. IsEnforced True means the policy is loaded and active. Do not let the word fool you: it is still an audit mode policy, so it blocks nothing.

Here is the Group Policy way. In the Group Policy Management Editor, go to Computer Configuration, Policies, Administrative Templates, System, Device Guard. Open Deploy App Control for Business. Select Enabled, then type the path of the policy file in the Code Integrity Policy file path box. Now remember the two limits. This setting takes only a single format policy file, and computers apply it at the next restart. That is why the lab only looks at this setting on DC01 and does not use it.

App Control reports in Event Viewer. Open Applications and Services Logs, Microsoft, Windows, CodeIntegrity, Operational. Event 3076 is the main audit event. It means this file would have been blocked if the policy were enforced. Event 3089 adds the signature details of that same file. Event 3099 means a policy was loaded, so you can confirm your policy is active. The fourth number to know is 3077. That one means an enforced policy actually blocked a file. Because we stay in audit mode, you will not see 3077 in the lab.

You can read the same log with PowerShell. Get-WinEvent reads the CodeIntegrity Operational log. Filter for IDs 3076 and 3077, and group them to count each one. The count differs on every computer, which is normal. There is no 3077 line, because nothing was blocked. Then filter for event 3076 with a message that contains hello dot exe, our unsigned test program, and show the first one. The message names the file in C colon Users Public that would have been blocked.

First, stop the deployment. If a Group Policy Object or an Intune profile still deploys the policy, it comes right back. Second, remove it with CiTool dash rp and the policy ID. Third, restart if your version needs it. From the Windows 11 2024 update on, an unsigned policy goes away without a restart. Fourth, check with CiTool dash lp that SA1 Audit CLIENT01 is gone. One big warning: never just delete a signed policy. Windows can fail to start. You deploy a signed replacement first, as Microsoft Learn describes.

Four mistakes to avoid. One: deploying a new allow list straight in enforced mode. Start in audit mode, read the 3076 events, fix the policy, and only then enforce. Two: trusting a user-writable folder with a FilePath rule. App Control ignores that rule at run time, so use Publisher or FilePublisher rules. Three: pushing a multiple-format dot cip file with the Group Policy setting. That setting takes the single format only. Four: deleting a policy while a GPO or Intune still deploys it. Turn off the deployment first, then remove it with CiTool.

One: yes, hello dot exe ran. 3076 is an audit event, so it would have been blocked only if the policy were enforced. 3077 means an enforced policy really blocked it. Two: option 3, Enabled colon Audit Mode. Remove it with Set-RuleOption dash Option 3 dash Delete, convert again and redeploy, but only after testing. Now on CLIENT01. I make two test programs in C colon Users Public: a copy of whoami, which keeps its Microsoft signature, and hello dot exe, which nobody signed. I copy DefaultWindows Audit, reset its ID, name it SA1 Audit CLIENT01, and confirm audit mode. I convert it to a dot cip file and deploy it with CiTool, and it shows as active. An allow list stops unknown code, and you always start in audit mode. Start from an example such as DefaultWindows underscore Audit. Rule options switch the policy's modes, and rule levels decide how files are matched. The multiple policy format uses policy ID dot cip files, with base and supplemental policies. Deploy with CiTool, Intune, or Group Policy for single format. Event 3076 means would block, 3077 means blocked, and CiTool dash rp removes a policy.
