Welcome to Topic 6.1, Group Policy Basics, the start of Learning Plan 6. Now you make every computer and user behave the way you want, from one place. You will learn what Group Policy does and where a GPO lives. You will tell computer settings from user settings, and predict which GPO wins with LSDOU, link order and precedence. You will use Block Inheritance and Enforced, create and link GPOs in the console and in PowerShell, and prove the result with gpupdate, gpresult and Group Policy Modeling.

Group Policy lets you set a setting once, in Active Directory, and every computer and user in scope applies it by itself. The setting lives in a Group Policy Object, or GPO. A GPO on its own does nothing. You link it to a site, the domain or an OU. Link SA1 Student Desktop to the Students OU, and Dev, Erin and every new student get it. For the Server+ exam, think centralized configuration: one baseline, and drift is fixed at the next refresh.

Every GPO is stored in two halves, and both carry the same ID, a GUID. The Group Policy container is an object in Active Directory, under Policies in the System container. It holds the name, version and status. The Group Policy template is a folder in SYSVOL on every domain controller. It holds a file called GPT dot INI and the Machine and User folders with the actual settings. The link is a third piece. It is stored on the site, domain or OU, which is why one GPO can be linked in many places.

Every GPO has two halves inside. Computer Configuration applies to computer objects in the linked OU. Windows applies it when the computer starts, and then in the background. The logon message on CLIENT01 is a computer setting. User Configuration applies to user objects in the linked OU, at sign-in and then in the background. Blocking Control Panel for dpatel is a user setting, and it follows him to any PC. Each half has two nodes. Policies are enforced, and they disappear when the GPO stops applying. Preferences only set a starting value.

Administrative Templates are the thousands of registry-based settings, such as Prohibit access to Control Panel. ADMX files define the settings, and ADML files hold the words for a language, like English. Each setting writes a value under a Policies key in the registry. With no central store, which is how our pod starts, the editor reads the templates from C Windows PolicyDefinitions on the computer you work on. A central store is one PolicyDefinitions folder in SYSVOL that every administrator uses. New templates are a download from Microsoft, and our pod has no internet, so we use the built-in ones.

When does a setting arrive? Computer Configuration applies when the computer starts. User Configuration applies when the user signs in. After that, Windows checks again in the background every 90 minutes, plus a random extra of up to 30 minutes, so that hundreds of clients do not all ask at the same moment. Domain controllers check every 5 minutes. So in the worst case a change takes about two hours to reach a client. If you cannot wait, run gpupdate dash force on the client.

GPOs are applied in a fixed order, and you can remember it as LSDOU. First the local policy on the computer. Then GPOs linked to the site. Then the domain, where the Default Domain Policy lives. Then the OUs, parent first and child last. When two GPOs set the same setting in different ways, the one applied last wins. That means the OU closest to the object wins, unless a link higher up is Enforced. For Dev Patel, that is the link on Students.

By default, settings flow down. A GPO linked to Lakeshore reaches Students, Staff and every other child OU. That is inheritance. Block Inheritance is a setting on an OU. Turn it on for Staff and GPOs linked above Staff no longer reach it, and GPMC marks the OU with a blue exclamation mark. Enforced is a setting on a link. An enforced GPO cannot be overridden by lower links, and it passes straight through Block Inheritance. So the rule to remember is simple: Enforced beats Block.

When several GPOs are linked to the same OU, link order decides. Link order 1 is applied last, so it wins a conflict. To see the full picture for an OU, open its Group Policy Inheritance tab. It lists every GPO that reaches the OU, and precedence 1 wins. Every domain also has two default GPOs. The Default Domain Policy is linked to the domain and holds password, lockout and Kerberos policy. The Default Domain Controllers Policy covers the domain controllers. Leave them for those jobs and create a new GPO for everything else.

Your main tool is the Group Policy Management Console, or GPMC, from Server Manager's Tools menu. Expand the forest, Domains and sa1.lab, and you see the OU tree with its links. To create and link in one step, right-click the OU, here Students, and choose Create a GPO in this domain, and Link it here. Name the GPO for its job, SA1 Student Desktop. Block Inheritance is on the same right-click menu. Right-click a link for Edit, Enforced and Link Enabled.

Edit opens the Group Policy Management Editor for that one GPO. Under User Configuration, Policies, you find Administrative Templates, and the label tells you the templates come from the local computer, because there is no central store yet. Open Control Panel and double-click Prohibit access to Control Panel and PC settings. Choose Enabled and select OK. There is no Save button. The GPO changes in Active Directory and SYSVOL right away, and clients pick it up at their next refresh.

The GroupPolicy module does the same work in PowerShell. New-GPO creates an empty GPO, and you can pipe it straight into New-GPLink with the target OU. Set-GPRegistryValue can write registry-based settings, like the Control Panel setting, but not every setting has a cmdlet. Security options such as the logon message are set in the editor. Finally, Get-GPInheritance shows an OU's own links, whether it blocks inheritance, and the inherited links in precedence order. That last line is what a client in Students gets.

Here is how those ideas look in GPMC. Right-click an OU, such as Staff, and choose Block Inheritance, and the blue exclamation mark appears. Right-click a link, such as SA1 Student Desktop under Lakeshore, and choose Enforced, and a padlock appears on it. Now select Students and open the Group Policy Inheritance tab. The enforced link from Lakeshore sits at precedence 1, above the link on Students itself, because nothing can override an enforced GPO. In PowerShell, use Set-GPInheritance and Set-GPLink.

Always test on a real client. On CLIENT01, signed in as dpatel, run gpupdate dash force. Then run gpresult slash r slash scope user. It shows the user's distinguished name, the domain controller that delivered the policy, and the list of applied GPOs, where you should see SA1 Student Desktop. For the full picture, gpresult slash h writes an HTML report. One catch: the computer part of gpresult needs an administrator window, so sign in as an admin for that.

GPMC has two wizards for checking. Group Policy Results reads what really applied on a computer for a user who signed in there, much like gpresult. Group Policy Modeling asks a domain controller what would apply for any user and computer, before you change anything, so it is perfect for planning. Its Advanced Simulation Options page even simulates loopback processing. Loopback makes user settings follow the computer, which suits shared lab PCs or Remote Desktop servers. Merge adds the computer's user settings to the user's own. Replace uses only the computer's.

Four common mistakes. One: linking a GPO with user settings to the Workstations OU. User settings follow user objects, so link it where the users are, or use loopback on purpose. Two: putting everything into the Default Domain Policy. Keep it for password, lockout and Kerberos policy, and create one new GPO per job. Three: expecting changes instantly. Wait for the refresh or run gpupdate dash force, and prove the result with gpresult. Four: using Block Inheritance and Enforced everywhere. Fix the OU design first.

Time to check yourself, using the Lakeshore tree. First, a GPO with only User Configuration settings is linked to Workstations. Does dpatel get those settings when he signs in to CLIENT01? Second, the Default Domain Policy and a GPO on Students set the same setting in opposite ways. Which one wins for dpatel? Third, Staff blocks inheritance, and a GPO linked to Lakeshore is Enforced. Does it reach cdiaz? Fourth, you changed a GPO ten minutes ago, and CLIENT01 does not show it yet. What do you run? Pause the video and answer.

Here are the answers. One: no. Dev Patel's user object is in Students, not Workstations, and user settings follow the user, unless loopback is turned on. Two: the GPO on Students wins. In LSDOU order the OU is applied after the domain, so it has the last word. Three: yes. Enforced passes through Block Inheritance, while the non-enforced GPOs from above stay blocked. Four: run gpupdate dash force on CLIENT01, then gpresult slash r, and look for the GPO in the list of applied Group Policy Objects.

Let me show you on the pod. In GPMC on DC01, I find the two default GPOs and their links. I create SA1 Student Desktop on the Students OU and enable the Control Panel setting. Then PowerShell creates the logon message GPO and links it to Workstations, and I set the title and text in the editor. On CLIENT01 I run gpupdate dash force and sign out, and the message appears before sign-in. No restart needed. As dpatel, Control Panel is blocked, and gpresult names the GPO. Finally I link the GPO to Lakeshore, block Staff, enforce the link, and read the precedence list.

To wrap up. A GPO is a container in Active Directory plus a template in SYSVOL, and links put it to work. Computer settings follow computers and user settings follow users. LSDOU sets the order, the closest OU wins, link order 1 wins, and Enforced beats Block Inheritance. Leave the default GPOs for their jobs and make one GPO per job. Refresh with gpupdate dash force and prove it with gpresult or Modeling. In Lab 6.1 you do all of this on DC01 and CLIENT01, in about 75 minutes.
