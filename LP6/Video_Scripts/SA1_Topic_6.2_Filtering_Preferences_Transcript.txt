Welcome to Topic 6.2, Filtering and Preferences. In Topic 6.1 you linked GPOs to OUs. Now you decide exactly who gets them. You will see the three gates every GPO passes. You will filter a GPO to one group, and learn why computers still need to read it since a 2016 security update. You will build a WMI filter that only workstations pass. Then you will meet Group Policy preferences, map a drive with one, and target it to a single group. As always, you will see the PowerShell for each task.

Linking a GPO is only the start. Think of three gates. Gate one is the link: the GPO must be linked to a site, the domain or an OU above the user or computer. Gate two is the security filter: the user or computer needs two permissions on the GPO, Read and Apply group policy. Gate three is optional, a WMI filter: a query that must be true on the computer. By default every new GPO gives Authenticated Users both permissions, so everyone in scope gets it. Security filtering means changing that list.

Here is security filtering in Group Policy Management. Select SA1 Student Desktop and look at the Scope tab. Under Security Filtering you normally see Authenticated Users. Select it and choose Remove. Then choose Add, type GG-Students, check the name and select OK. Now only members of GG-Students have Read and Apply group policy. That sounds finished, but it is not. When you removed Authenticated Users, the computers lost their Read permission too. The next slide shows why that matters so much.

In June 2016, security update MS16-072 changed one detail. Windows now reads a user's GPOs with the computer's account, not the user's. So when dpatel signs in on CLIENT01, the computer account CLIENT01 dollar must read the GPO first. It is not in GG-Students. If only GG-Students is on the GPO, the read fails and dpatel gets nothing, with no clear message on screen. The fix: give Authenticated Users, or Domain Computers, Read only. Read without Apply lets computers read the GPO but applies it to nobody.

You make that fix on the Delegation tab of the GPO. It lists every group and its allowed permissions. Select Add, type Authenticated Users, and in the Add Group or User box leave Permissions on Read. Do not choose an edit permission. Look at the list afterwards. GG-Students shows Read, from Security Filtering. That wording means Read plus Apply group policy. Authenticated Users shows plain Read, with nothing in brackets. That means it can read the GPO but does not apply it. Both entries are what you want.

In PowerShell the same work takes two commands. Set-GPPermission with permission level GpoApply gives GG-Students Read and Apply. Then Set-GPPermission for Authenticated Users with GpoRead and the Replace switch. Replace matters: without it, a higher permission like GpoApply would stay in place. Get-GPPermission with All lists every entry. Here I use a calculated property to show the trustee name. Authenticated Users has GpoRead, GG-Students has GpoApply, and domain controllers can still read. The filter is set and computers can read.

The third gate is the WMI filter. WMI stands for Windows Management Instrumentation, and filters are written in WQL, the WMI Query Language. Each computer runs the query on itself. True means the GPO applies; false means it is skipped. Our query asks Win32_OperatingSystem for ProductType 1. ProductType 1 is a workstation like CLIENT01, 2 is a domain controller like DC01, and 3 is a member server like SRV01. A GPO can have only one WMI filter. Remember the cost: every computer runs the query at every refresh.

To build the filter, right-click WMI Filters in Group Policy Management and choose New. Name it Workstations only and add a short description. Under Queries select Add. Leave the namespace as root backslash CIMv2 and type the query: select star from Win32_OperatingSystem where ProductType equals 1. Select OK, then Save. The filter now exists, but nothing uses it yet. To use it, open the GPO, here SA1 Workstation Logon Message, and on the Scope tab pick it under WMI Filtering. Answer Yes.

A typo in a WMI filter makes it false everywhere, so test the query first. On CLIENT01, Get-CimInstance for Win32_OperatingSystem shows the caption, Windows 11 Enterprise, and ProductType 1. Then run the exact filter query with the Query parameter and count the results. One result means true. On SRV01 the same lines give 0, so the filter is false there. The GroupPolicy module has no cmdlet to create WMI filters, but on DC01 Get-GPO shows which filter a GPO uses: Workstations only.

Now the second half of the topic: preferences. In the editor, each configuration has a Policies folder and a Preferences folder. Policies enforce. The user sees the setting greyed out and cannot change it, and when the GPO stops applying, the setting is removed. Preferences set a starting value. The user can change it until the next refresh writes it again, and when the GPO stops applying, the value stays behind. That is called tattooing. Use policies for security and preferences for convenience. Server+ calls this configuration management.

Every preference item has an action. Create adds the item only if it does not exist yet. Replace deletes the item and creates it again, so every setting matches. Update changes only the settings you filled in, and creates the item if it is missing. Delete removes it. Update is the usual choice. With a drive map set to Update, if a user deletes drive S, the next sign-in maps it again. One link to remember: the option Remove this item when it is no longer applied switches the action to Replace.

Here is a drive map. In the editor go to User Configuration, Preferences, Windows Settings, Drive Maps, and choose New, Mapped Drive. Set Action to Update. Location is the UNC path, backslash backslash SRV01 backslash Shared. Select Reconnect, and under Label as type Shared, the name users see in File Explorer. Under Drive Letter choose Use, and pick S. Leave Connect as empty. A password stored in a GPO can be read from SYSVOL, so Microsoft warns against it. Leave the hide and show options at No change.

Every preference item has a Common tab. Run in logged-on user's security context makes an item run as the user instead of SYSTEM; drive maps already do. Remove this item when it is no longer applied undoes the item when it goes out of scope. Apply once and do not reapply runs it only one time. Then item-level targeting. Select Targeting to open the Targeting Editor, choose New Item, Security Group, and pick SA1 backslash DL-Shared-Read. Now only members of that group get drive S.

Drive maps are just one kind of preference. A Registry item writes a key or a value; in the lab you write Lab equals SA1 under HKEY_CURRENT_USER, Software, Lakeshore, with Update. Shortcuts put a link on the desktop or the Start menu, for example to the college portal. Local Users and Groups can add a domain group, like GG-IT, to the local Administrators group on servers. Never put passwords there. And there are many more: files, folders, printers, scheduled tasks and services, all with the same actions.

PowerShell can do part of this. New-GPO piped into New-GPLink creates SA1 Drive Maps and links it to OU Lakeshore in one line. Set-GPPrefRegistryValue creates the registry preference item, with context User, action Update, the key, the value name and the value. Drive Maps and item-level targeting have no cmdlet, so you build those in the editor. Then check on the client. On CLIENT01, signed in as dpatel, net use shows drive S connected to backslash backslash SRV01 backslash Shared.

Here are four mistakes to avoid. One: removing Authenticated Users and nothing else. Users then get nothing; add it back with Read only. Two: a WMI filter that is never true, from a typo or the wrong ProductType. Test the query with Get-CimInstance first. Three: using a preference for something that must be enforced. Users can change preferences, and they tattoo. Four: expecting drive S right after gpupdate. Drive maps apply at sign-in, so sign out and in again. New group memberships also need a new sign-in.

Time to check yourself. SA1 Student Desktop is filtered to GG-Students, and SA1 Drive Maps maps S for DL-Shared-Read. First, only GG-Students is left on the GPO, and students get nothing. Why? Second, which ProductType does SRV01 report, and does Workstations only apply to it? Third, dpatel disconnects drive S by hand. What happens at the next sign-in? Fourth, alee is not in DL-Shared-Read. Does she get drive S, and does she get the Lab registry value? Pause the video and answer all four.

Here are the answers. One: since MS16-072 the computer reads user GPOs, and CLIENT01 dollar cannot read this one. Give Authenticated Users Read on the Delegation tab. Two: SRV01 reports 3, a member server, so the filter is false and gpresult shows Denied, WMI Filter. Three: drive S comes back, because the Update action maps it again at each sign-in. Four: no drive S, but yes to the registry value. Targeting works per item, and only the drive map is targeted to DL-Shared-Read.

Let's see it in the pod. On DC01 I open SA1 Student Desktop, remove Authenticated Users from Security Filtering, and add GG-Students. On the Delegation tab I add Authenticated Users back with Read only, and Get-GPPermission confirms it. Next I create the WMI filter Workstations only and pick it for the logon message GPO. Then I create SA1 Drive Maps on OU Lakeshore, add drive S with Update, and target it to DL-Shared-Read. On CLIENT01, dpatel gets drive S. alee signs in, and there is no S drive.

To wrap up. A GPO must pass three gates: the link, the security filter and an optional WMI filter. When you filter a user GPO, keep Read for the computers. WMI filters cost time, so test the query first. Preferences set defaults that users can change; policies enforce. Each preference item has an action, a Common tab and optional targeting.
