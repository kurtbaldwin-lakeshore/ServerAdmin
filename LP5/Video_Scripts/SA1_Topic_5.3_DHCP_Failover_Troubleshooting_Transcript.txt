Welcome to Topic 5.3, DHCP Failover and Troubleshooting. In Lab 5.2 you built one DHCP server, SRV01. That works, until SRV01 stops. In this topic you will see why one DHCP server is a single point of failure, and how the old split scope compares with DHCP failover. You will choose a failover mode and set the maximum client lead time. You will configure failover in the wizard and in PowerShell, and replicate changes to the partner. Then you troubleshoot clients without an address.

A lease is borrowed, not owned. With the 8-day lease from Lab 5.2, CLIENT01 tries to renew with SRV01 at half time, day 4. If SRV01 does not answer, at 87.5 percent, day 7, it asks any DHCP server. If SRV01 is down for an hour, clients with a lease hardly notice, but a new client gets nothing. If SRV01 is down for days, leases run out, and clients fall back to a 169.254 address. The fix is a second server that knows the same scope and leases.

The old fix was split scope. Two servers each held part of the range, often 80 percent on one and 20 on the other, with the rest excluded. But the servers shared no lease data, the small part could run out, and you set options and reservations twice. The current way is DHCP failover. Both partners hold the whole scope and copy every lease to each other. It works for IPv4 scopes only, with exactly two servers in a relationship. A relationship is the named link between them.

Failover has two modes. Load balance is the default. Both servers answer at the same time, and a hash of each client's MAC address decides which one answers. The split is 50 50 by default, and you can choose any percentage. In hot standby, the active server serves everyone and the standby waits. It keeps a reserve of addresses, 5 percent by default, for new clients during an outage. This fits a backup server at another site. Lab 5.3 uses load balance, 50 50.

Three more settings. Maximum Client Lead Time, or MCLT, limits how far a server may go beyond what its partner knows. Without its partner, it gives only short leases, MCLT long. The default is one hour. The state switchover interval is off by default. Turn it on, and a server that lost its partner declares it down by itself after the interval. The shared secret turns on message authentication, so a stranger cannot pose as a partner. Choose your own secret, never the pod password.

Each partner has a state. In Normal, the partners talk, and each serves its share. When contact is lost, a server goes to Communication Interrupted. It cannot tell whether its partner crashed or only the network broke, In load balance it then answers all clients, even its partner's. It renews their leases for the MCLT only, and gives new leases from its own free pool first. Partner Down is set by you, or by the switchover timer. After the MCLT, that server takes over the whole scope. When contact returns, the partners compare leases and go back to Normal on their own.

In the DHCP console on SRV01, right-click IPv4, or the scope, and choose Configure Failover. On the first page, clear Select all and tick the scope 192.168.50.0. Then type the partner server, SRV-CORE at 192.168.50.21. The partner must already run DHCP and be authorized in Active Directory. Clear the box that says Reuse existing failover relationships, because you want a new one. Then select Next to reach the most important page of the wizard, the one that creates the relationship.

On Create a new failover relationship, type the Relationship Name, SRV01-SRVCORE. It must be unique on both partners. Leave the Maximum Client Lead Time at 1 hour. Mode is Load balance, with 50 percent for the local server and 50 for the partner. Leave State Switchover Interval cleared, so you decide when a partner is really down. Keep Enable Message Authentication on and type your shared secret; it shows as stars. Then Next, Finish, and check that every task says Successful.

Here is the same job in PowerShell on SRV01. Read-Host with AsSecureString asks for the secret at a hidden prompt. The SharedSecret parameter wants plain text, so the next line converts it in memory only. Then Add-DhcpServerv4Failover: the name, the partner, the scope, 50 percent, an MCLT of one hour, and the secret. Dash Force skips a prompt. Remove-Variable clears the plain copy. Get-DhcpServerv4Failover then shows the relationship, LoadBalance, 50, one hour, and the state Normal. Run it on SRV-CORE too.

Here is a rule that surprises many people. Leases copy themselves between partners, but scope settings do not. If you change an option, a reservation, an exclusion or the lease time on SRV01, SRV-CORE keeps the old value until you replicate. Right-click the scope and choose Replicate Scope, or Replicate Relationship for every scope in it. In PowerShell, use Invoke-DhcpServerv4FailoverReplication. Careful: replication overwrites the partner. Always start it on the server that has the settings you want to keep, and make your changes on that one server only.

Now troubleshooting. A good Server+ habit: start at the client. On CLIENT01, ipconfig release and renew. If renew says it is unable to contact your DHCP server, no server answered. Look at ipconfig all. An Autoconfiguration address in 169.254, with mask 255.255.0.0, is APIPA: Windows picked its own address. It reaches no server and no DNS. So APIPA is a clue, not a fix. When the problem is solved, renew again, and you see a real address and the DHCP server that gave it.

Then move toward the server. If every client gets 169.254, check whether the DHCP Server service is stopped. If the service runs but never answers, check authorization: in a domain, a Windows DHCP server must be listed in Active Directory before it serves anyone. That stops rogue servers. If old clients are fine and new ones fail, the scope may be full. If the address is fine but names fail, check options 6 and 15. And if only another subnet fails, the router may lack a relay agent.

Three cmdlets cover most of that table. Get-Service DHCPServer shows whether the service is Running; if not, Start-Service. Get-DhcpServerInDC lists the authorized DHCP servers. In the lab you should see both SRV01 and SRV-CORE. If one is missing, authorize it with Add-DhcpServerInDC. Get-DhcpServerv4ScopeStatistics shows free and used addresses for each scope. Watch the PercentageInUse column, and run it on both partners. Near 100 means a full scope: widen the range or shorten the lease time so addresses come back sooner.

A new client has no address, so it shouts: it sends a broadcast. Routers do not forward broadcasts. So a client on 192.168.60.0 never reaches a DHCP server on 192.168.50.0, even when the right scope exists. The answer is a DHCP relay agent on that subnet, often called IP helper on routers. It catches the broadcast and forwards it to the servers. It adds its own address, so the server picks the matching scope. With failover, point it at both partners. Our pod has one subnet, so this is a concept.

Every DHCP server also keeps a plain text audit log in C colon backslash Windows, System32, dhcp, one file for each weekday, like DhcpSrvLog-Mon dot log. Read the end with Get-Content and dash Tail. Each line starts with an event ID, then the date, time, a description, the IP address, host name and MAC address. ID 10 is a new lease, 11 a renewal, 12 a release. ID 14 means the scope was full. IDs 54 and 56 mean the server was not authorized.

Four mistakes to avoid. One: changing an option or reservation on one partner only. Replicate from the server with the right settings. Two: expecting failover for DHCPv6 or for three servers. Failover is IPv4 only, two servers per relationship. Three: typing the shared secret into a script, or reusing the pod password. Choose your own and type it at a hidden prompt or in the wizard. Four: installing the second server but never authorizing it. Check that Get-DhcpServerInDC lists both.

Time to check yourself. SRV01 and SRV-CORE share the scope 192.168.50.0. First, CLIENT01 shows 169.254.23.7. What does that tell you, and where do you look first? Second, you change option 6 on SRV01. Why can a client still get the old value? Third, SRV-CORE moves to a small backup site. Which mode fits better now? Fourth, clients on 192.168.60.0 behind a router get no address, but the scope exists. What is missing? Pause the video and answer all four questions.

Here are the answers. One: 169.254 is APIPA, so no DHCP server answered. Check the client's network, then the DHCP Server service on both partners, then authorization. Two: scope settings do not replicate by themselves, so SRV-CORE still has the old option. Replicate the scope from SRV01. Three: hot standby. The local server serves everyone, and the remote partner keeps its 5 percent reserve for an outage. Four: a relay agent on the router, because broadcasts stop at the router.

Let's watch it in the pod. On SRV01 I open the DHCP console and run Configure Failover for our scope, with SRV-CORE as partner, load balance 50 50, and a secret I type off camera. On SRV-CORE the scope and the CLIENT01 reservation are already there. Now I change the lease time on SRV01. SRV-CORE still shows 8 days, until I choose Replicate Scope. Next I stop DHCP on SRV01. CLIENT01 still gets 192.168.50.150, now from SRV-CORE. I stop SRV-CORE too, and CLIENT01 falls back to a 169.254 address.

To wrap up. Failover replaces split scope: two servers, one IPv4 scope, shared leases. Load balance shares the clients; hot standby waits with a 5 percent reserve. Keep MCLT at one hour, switchover off, and use your own shared secret. Replicate scope changes by hand, from the right server. And when a client shows 169.254, work from the client to the server: service, authorization, scope, relay.
