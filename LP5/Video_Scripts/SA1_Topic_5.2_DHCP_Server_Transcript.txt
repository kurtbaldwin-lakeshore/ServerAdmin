Welcome to Topic 5.2, DHCP Server. So far every pod address was typed by hand. Now a server takes over that job. You will learn how a client gets an address with four messages called DORA, and how leases renew. You will install the DHCP Server role on SRV01, finish its post-install wizard, and see why the server must be authorized in Active Directory. Then you build a scope with options, reserve an address, and test it all from CLIENT01.

DHCP stands for Dynamic Host Configuration Protocol. It hands out IPv4 settings automatically. Servers like SRV01 keep static addresses, and clients ask. A few words to learn. A scope is one subnet's range of addresses the server may lease. A lease is permission to use one address for a set time, eight days by default. Options are the extra settings that ride along, like the gateway and DNS server. An exclusion is never handed out, and a reservation always goes to the same client.

How does a client with no address get one? Four messages, called DORA. First, Discover: is any DHCP server out there? Second, Offer: the server suggests an address, a lease time and options. Third, Request: the client says, I take that offer. Fourth, Acknowledge: the server confirms, and the lease starts. Discover and Request are broadcasts, because the client has no address yet. Offer and Acknowledge can be broadcast or unicast. The server listens on UDP port 67 and the client on UDP 68. Another subnet needs a relay agent.

Take the default eight-day lease. At fifty percent, day four, the client sends a unicast request straight to SRV01 to renew. If SRV01 agrees, the clock restarts. If SRV01 is silent, the client keeps trying, and at eighty-seven and a half percent, day seven, it rebinds by broadcasting to any DHCP server. If the lease runs out, the client drops the address and starts DORA again. With no server at all, it ends up with an APIPA address in 169.254.

Installing the role looks just like installing AD DS. In Server Manager on SRV01, choose Manage, Add Roles and Features. On Server Roles, select DHCP Server, then Add Features so you get the DHCP console and PowerShell module. No restart is needed. When it finishes, Server Manager raises a flag: configuration required for DHCP Server at SRV01, with the link Complete DHCP configuration. In PowerShell, one line does it: Install-WindowsFeature DHCP, dash IncludeManagementTools. The role alone leases nothing yet.

The flag link opens the DHCP Post-Install configuration wizard. Description tells you the two jobs it will do: create the local groups DHCP Administrators and DHCP Users, and authorize the server in Active Directory. On Authorization, keep Use the following user's credentials with SA1 backslash Administrator. That account belongs to Enterprise Admins, which is who may authorize. Select Commit. The Summary page should show Done for security groups creation and Done for authorizing the DHCP server. Close it and the flag clears.

Why does authorization exist? A rogue DHCP server is one nobody approved. Its offers could send clients to a wrong gateway or a fake DNS server. In a domain, a Windows DHCP server checks a list in Active Directory before it leases. If its name is on the list, like SRV01, it works. If not, it leases nothing. The limit: only Windows DHCP servers check that list. A home router plugged into a wall port does not, and switches stop those with DHCP snooping.

Here are the wizard's jobs in PowerShell. Add-DhcpServerSecurityGroup creates the two groups; older guides use netsh dhcp add securitygroups for the same thing. Then restart the DHCPServer service so they apply. Add-DhcpServerInDC, with the name srv01.sa1.lab and the address 192.168.50.20, puts SRV01 on the authorized list. Get-DhcpServerInDC reads the list back, and you should see that one line. Last, a Set-ItemProperty on a Server Manager registry key tells Server Manager the post-install work is done, so the flag goes away.

Now the scope. Open the DHCP console, expand srv01.sa1.lab, right-click IPv4 and choose New Scope. Name it SA1 Clients, a label for people. On IP Address Range, start at 192.168.50.100 and end at 192.168.50.199, with a mask of 255.255.255.0. Our servers use .10 to .50, so they stay outside the range. The scope ID becomes 192.168.50.0. On Add Exclusions and Delay, exclude .100 to .109 and select Add. Those ten addresses are kept back for devices you set by hand.

The wizard continues. Lease Duration shows eight days, the default, so keep it. Say yes to configuring options now. On Router, Default Gateway, add 192.168.50.1. That is option 003. The pod has no router, so this is only option data on the client side. On Domain Name and DNS Servers, the parent domain is sa1.lab, option 015, and the DNS server is DC01, 192.168.50.10, option 006. Skip WINS. Finally, activate the scope now, because only an active scope answers clients.

The whole wizard fits in three commands. Add-DhcpServerv4Scope takes the name, start and end of the range, the subnet mask and the lease duration of eight days. Scopes are active by default. Add-DhcpServerv4ExclusionRange uses dash ScopeId, the network address 192.168.50.0, to pick the scope, then the start and end of the exclusion. Set-DhcpServerv4OptionValue sets the router, the DNS server and the DNS domain in one go. Dash DnsServer validates the DNS server address, unless you add dash Force, so keep DC01 running. The two Get commands prove it worked.

In the DHCP console, your scope sits under IPv4. Inside it, Address Pool holds the range and exclusions, Address Leases shows who has which address, and Reservations holds fixed ones. Scope Options shows 003, 006 and 015 for this scope only. Further down, Server Options apply to every scope on SRV01. What if the same option is set in two places? The most specific one wins. Reservation beats scope, and scope beats server. The gateway differs per subnet, so it belongs on the scope.

A reservation always gives a client the same address. Under the scope, right-click Reservations and choose New Reservation. Give it a name, CLIENT01, and the address 192.168.50.150. It is inside the range, outside the exclusion. Then type the client's MAC address, which you read as Physical Address in ipconfig slash all. One wrong character means no match. Why not just a static address? A reservation is managed in one place, and the client still receives all the options.

In PowerShell, Get-DhcpServerv4Lease lists the active leases in the scope. CLIENT01's first address can be anything free from .110 to .199. Look at the ClientId column. For Windows clients, that is the MAC address. So instead of typing, you can grab it from the lease into a variable, then run Add-DhcpServerv4Reservation with the scope, the address .150, that ClientId and the name. After CLIENT01 releases and renews, list the leases again. The address is now .150 and the state reads ActiveReservation.

On CLIENT01, ipconfig slash all is your best friend. Physical Address is the MAC you need for a reservation. DHCP Enabled says Yes. The IPv4 address, the gateway, the DNS server and the DNS suffix all came from the scope. DHCP Server names who gave the lease, 192.168.50.20. To get a new lease, run ipconfig slash release to give the address back, then slash renew to run DORA again. By default CLIENT01 registers its own A record, and SRV01 would register the PTR record if a reverse zone existed.

Four mistakes. One: skipping authorization in a domain. The role and scope look fine, but nothing gets leased. Authorize, then check with Get-DhcpServerInDC. Two: a range that covers static addresses. Keep servers outside the range or exclude them, or two machines will fight over one address. Three: pointing option 006 at a public or wrong DNS server. Domain clients must ask a domain controller, here 192.168.50.10. Four: a reservation with a mistyped MAC address. Copy it carefully, then release and renew.

Time to check yourself. SRV01 leases from SA1 Clients for eight days. First: name the four DORA messages in order, and say why the first one is a broadcast. Second: when does CLIENT01 first try to renew its lease, and whom does it ask? Third: the role and scope are in place, but no client gets an address. Which step was most likely skipped? Fourth: option 006 differs between server options and scope options. Which value does CLIENT01 get? Pause and answer.

Here are the answers. One: Discover, Offer, Request, Acknowledge. The first is a broadcast because the client has no address and knows no server yet to ask. Two: after four days, at fifty percent, with a unicast request straight to SRV01. At seven days it broadcasts to any server. Three: authorization in Active Directory. An unauthorized Windows DHCP server in a domain leases nothing. Four: the scope option, because the most specific level wins: reservation first, then scope, then server.

Let's build it. On SRV01 I add the DHCP Server role, then use the flag to run the post-install wizard with SA1 Administrator and commit. The console shows green checks. Now a new scope: SA1 Clients, .100 to .199, excluding .100 to .109, eight days, with router, DNS server and domain. On CLIENT01 I switch to automatic addressing, and ipconfig shows a lease from SRV01. Back on SRV01 I reserve .150 for CLIENT01's MAC. Release, renew, and there it is: 192.168.50.150.

A client gets an address with DORA: Discover, Offer, Request, Acknowledge, over UDP 67 and 68. It renews at fifty percent, rebinds at eighty-seven and a half, and falls back to APIPA. To build a server, install the role, create the groups and authorize it in Active Directory. A scope is a range plus exclusions, a lease time and options 003, 006 and 015. Reservations tie an address to a MAC. Lab 5.2 practices it all in about an hour.
